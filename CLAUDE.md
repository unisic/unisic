# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

```sh
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/unisic
```

Requires `qt6-qtbase-devel qt6-qtdeclarative-devel qt6-qtsvg-devel pipewire-devel` (Fedora) plus runtime `ffmpeg` and `wl-clipboard`. `pipewire-devel` is optional - without it the build succeeds but recording is disabled (`HAVE_PIPEWIRE` guard). Same pattern for OCR: `tesseract-devel leptonica-devel` + a langpack like `tesseract-langpack-pol` enable it (`HAVE_TESSERACT`); `zxing-cpp-devel` additionally enables QR/barcode decoding inside the OCR path (`HAVE_ZXING` - a code in the region copies its payload instead of OCR-ing its pixels). The capture popup positions itself by filling the screen and masking input to the card (no layer-shell dependency). `ctest --test-dir build` runs the QtTest targets in `tests/` (pure-logic units - version compare, shortcut format, annotation canvas, history filter); everything compositor-bound is covered by the in-app smoke test instead.

**End-user install: `scripts/install.sh`** (NOT part of the build; run `bash <(curl -fsSL https://raw.githubusercontent.com/unisic/unisic/main/scripts/install.sh)`, or `curl … | bash` - the menu reads `/dev/tty`, so a pipe still works). A single self-contained bash script that is **TUI-only, no CLI** (deliberately - see the iteration history): running it opens a **btop-style bordered arrow-key menu** in the terminal's **alternate-screen buffer**, so the whole run (menu *and* install output) lives in its own "window" and the terminal is restored to the command line on exit, leaving only a thank-you. It is ONE morphing menu: the main screen offers **Install or update / Settings / Remove / Quit** under a green install-status line (`installed_status()`: what's installed + auto-update state, or "not installed yet"), and each of the first three opens its own submenu - Install (recommended install / portable / "install a specific version" → version picker), Settings (auto-updates timer toggle + pre-release toggle, both flip in place), Remove (uninstall ± delete settings). Full-redrawn in place each key, never a second screen; `q`/Esc backs out one level (submenu → main, version picker → Install). The only non-interactive entry is the private `--self-update <appimage|tarball|native> <prefix> [pre]`; the auto-update timer runs the portable channels, and Unisic's in-app "Install now" (native `/usr` package installs only - see `UpdateChecker::installViaScript`) runs the `native` channel inside a terminal it spawns so the `sudo` prompt has somewhere to go. There are no user-facing flags. It auto-detects the distro from `/etc/os-release` and installs the matching GitHub release asset: `.deb` (Debian/Ubuntu apt), `.fedora.x86_64.rpm` (**Fedora only** - the rpm links Qt PRIVATE symbols, locked to Fedora's exact Qt minor), `.pkg.tar.zst` (Arch), or adds the OBS zypper repo on openSUSE; **atomic/immutable desktops** (Silverblue/Kinoite/Bazzite/…, detected via `/run/ostree-booted`) and any distro with no native package get the self-updating **AppImage** / portable `.tar.gz` in `~/.local` (no password). Each native package self-registers its OBS/COPR update repo, so re-running also updates; the menu also uninstalls (± delete settings), installs **older versions** (version picker), and toggles a **systemd-user daily auto-update timer** (portable channels) + pre-releases. On an **X11** session it warns after install that screen recording won't work (screenshots/annotate/upload do; recording needs the Wayland-only ScreenCast portal - verified in `src/capture` vs `src/record`). If release-asset naming, the update repos, or supported channels change, update this script too. Details live in `AGENTS.md` §3.

**Flatpak / Flathub: `packaging/flatpak/`** (manifest + `build.sh` + a README that is the submission checklist). The KDE runtime covers Qt 6, KF6 and PipeWire; the manifest additionally builds **x264 + ffmpeg** (the runtime's ffmpeg has NO software H.264 encoder, so MP4 recording would need a VAAPI GPU and the GIF pipeline's `libx264rgb` intermediate would fail outright; `org.freedesktop.Platform.ffmpeg-full` is not usable, it stops at branch 24.08 while KDE 6.11 is 25.08), leptonica + tesseract + `eng`/`pol` traineddata (the sandbox cannot read host langpacks), zxing-cpp, wl-clipboard and layer-shell-qt. **Six code paths branch on `FLATPAK_ID`**, each because the sandbox makes the normal route impossible, not as a preference: `KWinScreenShot2::isAvailable` returns false (KWin authorizes its restricted interface by the caller's exe path against the installed .desktop, which a sandboxed client can never match); `registerHostAppId` and `PortalGlobalShortcuts::registerAppId` skip the self-assignment (identity comes from the sandbox metadata); `PortalScreenshot::candidateAppIds` grants the silent-screenshot permission to the flatpak id ALONE (never the anonymous `""` host bucket); `execStagedUpdate` never stages; `UpdateChecker::installKind()` is `"flatpak"` and `updatesManagedExternally()` turns the whole Updates pane into an explanation - no GitHub request at all, because the only possible outcome would be "go run flatpak update"; and autostart goes through `org.freedesktop.portal.Background.RequestBackground` (`autostart: true` + `commandline`), because `$XDG_CONFIG_HOME/autostart` inside the sandbox is `~/.var/app/<id>/config`, which the host session never reads. The portal has no getter, so the ANSWER it gave is persisted as `ui/portalAutostartGranted` - a refusal leaves the switch off, which is the honest reading.

**AUR: `packaging/aur/`** (`unisic` source build + `unisic-bin` release repack + `sync.sh` + a README that is the publish checklist). Deliberately NOT `packaging/arch/PKGBUILD`, which feeds OBS and the release asset and whose `unisic.install` appends the OBS pacman repo to `/etc/pacman.conf`: an AUR package may never enable a third-party repo, and here it would also fight the helper. **pacman cannot use the AUR as a repository** - the AUR hosts recipes, not built packages, so there is no sync DB for `pacman -Syu`. Only a helper (`paru`/`yay`/`pikaur`/`trizen`/`aura`/…, never yay alone) updates an AUR package, by matching *foreign* packages (`pacman -Qm`) against the AUR **by name** - which is also how a directly downloaded `.pkg.tar.zst` named `unisic` gets adopted, and why a successfully registered OBS repo instead keeps it non-foreign. Exactly one channel ever owns an install. Both recipes install `/usr/share/unisic/install-channel` containing `aur`; `UpdateChecker::installKind()` reads it (value WHITELISTED so a stray file cannot invent a kind, cached, resolved from `applicationDirPath()/../share` so a non-`/usr` prefix works) and `updatesManagedExternally()` then covers flatpak ∨ aur, which kills the GitHub check and both install buttons - "Install now" runs `install.sh --self-update native`, which `pacman -U`s the GitHub package OVER the helper's AND appends the OBS repo. `install.sh` carries the same guard (`aur_owned()` - the marker or an installed `unisic-bin`, NOT `pacman -Qm`, which a failed-repo direct install also matches - plus `aur_helper()`), and prefers a helper for fresh Arch installs; because "Install now" fetches `install.sh` fresh from the repo every time, that guard protects releases built before the marker existed. **Source tarballs**: GitHub's tag archives NEVER contain submodules, so from the `external/unisic-kit` split onward the `unisic` recipe needs a second kit tarball pinned by commit (or a complete source tarball published as a release asset) - see the README. `sync.sh` retargets both recipes at a release, refuses to publish when the released package needs a dependency the recipes lack (extras are fine - `libinput`/`hicolor-icon-theme` are namcap findings upstream still under-declares), and regenerates `.SRCINFO` with `makepkg --printsrcinfo` in a container, because the AUR web interface reads `.SRCINFO` and not the PKGBUILD. The `aur` job in `release.yml` runs all of that after each release (unprivileged `builder` + passwordless sudo, since makepkg refuses root and `-s` needs sudo; `AUR_SSH_KEY` secret; `aur.archlinux.org`'s host key PINNED, never `ssh-keyscan`), with `--check bin` only - the `arch` job already compiled this tree, so building the source recipe again verifies nothing - and it SKIPS pre-releases, because an AUR name with no channel in it means stable.

## Architecture

- `src/AppContext.*` - facade exposed to QML as context property `App`; owns all subsystems and the after-capture pipeline (editor/save/clipboard/upload/history), tray icon, hotkey dispatch.
- **The installed `.desktop` `Exec` must be an ABSOLUTE path** (`resources/app.unisic.Unisic.desktop.in` + `UNISIC_DESKTOP_EXEC`, configured from `CMAKE_INSTALL_FULL_BINDIR`). KWin authorizes a caller for its restricted interfaces by comparing `QFileInfo(splitCommand(Exec).first()).canonicalFilePath()` against `/proc/<pid>/exe`; a bare `unisic` resolves against KWIN's working directory, matches nothing, and `canonicalFilePath()` returns `""`, which can never equal `/usr/bin/unisic`. Up to 0.7.5 the installed file said `Exec=unisic`, so `org.kde.KWin.ScreenShot2` was refused on EVERY native package and silently fell back to the portal - invisible in development, where `ensureDesktopFile()` writes an absolute `applicationFilePath()`. Spectacle, krfb-virtualmonitor and xdg-desktop-portal-kde all install absolute Execs for the same reason. The AppImage job pins it back to the bare name on purpose (relocatable AppDir, and a transient FUSE mount can never satisfy the check anyway).
- `src/capture/` - backends: `KWinScreenShot2` (silent, needs the installed .desktop file's `X-KDE-DBUS-Restricted-Interfaces`; auto-falls back on auth failure) and `PortalScreenshot`; `PortalRequest` implements the portal Request/Response handle pattern; `ScreenCastSession` drives the ScreenCast portal for recording; `CaptureManager` picks the backend.
- `src/editor/AnnotationCanvas` - the core drawing surface (QQuickPaintedItem): all tools, selection, undo/redo, and final compositing in **image-pixel space** (DPR forced to 1.0). Used by both the overlay and the editor; export is exactly what's rendered.
- `src/overlay/OverlayController` - freezes each screen (one capture per monitor), spawns one fullscreen `OverlayWindow.qml` per screen, returns annotated crop (screenshots) or physical-pixel region (GIF). **Smart pick and U-2-Net background removal were REMOVED in 0.7.1b** - do not reintroduce without asking. `src/overlay/ObjectDetector.*` (pure-pixel line-pair/flood-fill/enclosed-interior detection driving a click-to-pick region overlay), `src/segment/U2NetSegmenter.*`, the whole `HAVE_ONNX`/onnxruntime CMake path, the editor's "Remove background" action and the Settings model-download UI are all gone: the detector never matched real windows reliably enough to ship on (it was EXPERIMENTAL, default OFF), and no packaging channel ever built onnxruntime in, so `HAVE_ONNX` was OFF in every shipped package - U-2-Net only ever ran in local dev builds. `AnnotationCanvas::Tool` keeps `ObjectPick = 13` as a RESERVED hole so the persisted enum values of the tools after it do not shift. The editor's smart eraser (`SmartErase = 12`) is unrelated and stays: it rebuilds the background under the stroke from the four boundary strips just OUTSIDE the rect (never from inside it - the object is in there). Each strip sample is the per-channel median of a 5-along × 3-out window; then the strips are CLEANED - ring median + 3·1.4826·MAD band marks outliers, which are re-interpolated from the inliers bracketing them - and only then interpolated as a **Coons patch**, clamped per pixel to the range of the four samples it interpolates. Computed at ≤192² and rescaled (smooth by construction, so the rescale is free); reuses Blur's `fxPatch` cache + `m_fxFast` drag rule; samples via `pixelColor` (converting a 4K base per drag move would rewrite ~33 MB). **Every one of those steps is load-bearing, do not simplify them away**: up to 0.7 it filled with ONE averaged colour sampled from the rect's OWN border, which read as a smudge; a plain Coons over raw strips then smeared the object across the patch whenever a stroke edge cut through it (the normal case - scrubbing over text) and overshot into bright bands. `tests/AnnotationCanvasTest.cpp` pins all three: `smartEraseFollowsGradientBackground` (flat fill → drift 41/255), `smartEraseOverlappingStrokesStayOnBackground` (no outlier rejection → drift 210/255), `smartEraseRebuildsFlatBackground`.
- `src/record/` - `PipeWireGrabber` (libpipewire thread, keeps latest SHM frame) → `GifRecorder` samples at fixed FPS into ffmpeg stdin (lossless x264rgb temp), then two-pass palettegen/paletteuse GIF conversion. `RecordBorderHelper` - the GNOME record-region frame: mutter has no layer-shell and no keep-above for xdg_toplevel, so `unisic --record-border-helper` (dispatched in main() BEFORE QApplication - must boot on xcb, and one process can't host two QPA platforms) draws an XWayland **override-redirect** window (mutter's topmost stacking layer, click-through via `WindowTransparentForInput`). The region travels as monitor FRACTIONS: XWayland renames RandR outputs (`XWAYLAND<n>`) and its coordinate space (logical vs physical layout mode) need not match the Wayland one, but the fraction of the monitor is invariant; the helper pads 2 px outward so rounding can never bleed the frame into the ffmpeg crop. Helper lifetime = parent's stdin pipe (EOF → quit - a crashed parent can't orphan the frame). `UNISIC_RECORD_BORDER=helper` forces this path on KDE for testing; `capRecordBorder()` = layer-shell ∨ X11 session ∨ KWin ∨ `$DISPLAY`.
- `src/upload/UploadManager` - destinations from `~/.config/unisic/destinations.json` (.sxcu-like; `$text$`/`$json:path$`/`$regex:$` extraction); `type: "curl"` shells out to curl for FTP/SFTP. **Never compile an Imgur Client-ID in**: it identifies the *application*, so one shipped ID puts every user on one ~1250/day cap and makes whoever registered it answerable to Imgur for strangers' uploads. The builtin ships with no Authorization header; the user pastes their own ID (DestinationsPage swaps the raw headers-JSON field for a Client-ID field on any `api.imgur.com` destination), `startUpload` refuses an ID-less Imgur upload with an actionable message (Imgur itself answers a bare 429), and `ensureBuiltins` strips the placeholder ID that shipped up to 0.7 from stored configs. **Test upload** (the server editor's button) is `testDestination(QVariantMap)` → `testFinished(ok, url, error)`: it takes the UNSAVED form state and pushes a generated 64² checkerboard PNG (the palette's Secondary/Accent, named constants at the top of the .cpp) through the same http/curl transport a real capture uses. It resolves the destination OBJECT and calls `startUploadTo`; passing a *name* would be wrong, because `destinationNamed()` silently falls back to the first stored destination for an unknown name, so an unsaved config would be "tested" against somebody else's server. Nothing is persisted: no `destinations.json` write, no history entry, no clipboard touch. A curl test really writes `unisic-test.png` to the user's own server and Unisic cannot delete it again, which the sheet says out loud before they press it.
- `src/history/HistoryStore` - the model itself stays a plain newest-first list; `src/history/HistoryFilterModel` (QSortFilterProxyModel, `QML_ELEMENT`) is the History page's search/filter layer (`searchText`, `kindFilter`, `favoritesOnly`, `uploadedOnly`). `kindFilter` matches `CategoryRole` (`"image"|"gif"|"video"|"replay"`), NOT `KindRole`: an instant-replay clip is an .mp4 that trims/plays/copies exactly like a recording, so it keeps kind `"video"` and separates only as a category. That needs `Entry::origin` (persisted `"origin": "replay"`), threaded from `GifRecorder::finished(path, fromInstantReplay)` - the export path is an .mp4 like any other, so nothing downstream can recover it. Entries written before 0.7.1 have no origin and fall back to the `Unisic_Replay_<stamp>.mp4` name every export gets. The page addresses entries by `EntryIdRole`, never by row (a proxy row means a different entry after a filter switch, and a batch delete shifts the rows behind it): `entryById`/`removeByIds`/`setFavoriteByIds`, plus `entryIds`/`entryIdsBetween`/`timestampAt` on the proxy for select-all, shift-range and the sticky date header (rows outside the viewport have no delegate, so QML cannot collect these itself).
- `src/notify/LayerShellNotifier` (layer-shell card) + `src/notify/NotificationHelper` (GNOME) - one `NotificationPopup.qml` and one `NotifCard.h` (style→size table, the settings the card reads, `effectiveSettings()` for the settings preview's unsaved overrides), two hosts. `notificationActionOrder` is a CSV of stable action ids; both hosts receive it in the same settings snapshot and QML normalizes it by dropping unknown/duplicate ids and appending newly introduced actions. Layer-shell → a card-sized overlay surface anchored to the corner. GNOME/mutter → the SAME QML on an XWayland **override-redirect** window in a second process (`--notification-helper`; one process can't host two QPA platforms), Steam-toast style. `AppContext::m_activePopupNotif` enforces one stylized card at a time; a newer capture dismisses the previous card through whichever host owns it, allowing an old helper process to exit normally. **The alternatives are dead ends, do not retry them**: a plain Wayland toplevel cannot place itself (no positioning protocol), and the fullscreen-surface-with-input-mask trick that works for the capture overlay renders **BLACK** on mutter - it unredirects fullscreen surfaces, so their transparency is never composited. Mutter can strand XWayland hover on "inside": once the pointer reaches a native Wayland surface, XWayland freezes its pointer position and even `XQueryPointer` keeps naming the card. Silence timeouts, pointer polling, and `org.gnome.Mutter.IdleMonitor` cross-checks are unreliable. Instead the helper keeps the existing 16 px transparent shadow gutter inside its X input shape, so crossing the visible card edge clears QML hover while the pointer still belongs to XWayland. Do not shrink the helper's input mask back to the exact card rect.
- `qml/components/UTour.qml` - the optional seven-step guided tour. **Not a modal Popup**: it is a plain `Item` filling the window under the title bar with a floating card in the bottom-right corner, and each step emits `pageRequested(page)` so `Main.qml` navigates `currentPage` to the page that step is talking about - the control being named is on screen, live and clickable, while you read about it. A modal would dim and cover exactly that page. The card has a `MouseArea` that swallows its own clicks and NOTHING else grabs input, so the sidebar and the page keep working; `Escape` closes through a `Shortcut`, not a `Keys` handler, because it deliberately holds no focus. Two steps offer a real action (`App.captureRegion()`, the `Ctrl+/` sheet) - a tour that says "you can do X" and then lets you do X. **Never auto-opened**: offered from the welcome send-off, otherwise Settings > General; `Settings::tourSeen` latches, `markSeenOnClose:false` on the manual path. Step 7's tool letters are read LIVE from `ToolCatalog.visibleFor("editor", "")`. **A spotlight cut-out remains impossible, do not retry it**: the overlay/editor controls belong to windows that do not exist while the main window is up, every page is behind a `Loader` destroyed on navigation, and a hole plus a follower tooltip under the pointer is what the layout rules forbid. Smoke-checked by `tourCardCheck()`, which COMPILES the card via QQmlComponent without instantiating it.
- `src/diag/` - the runtime log a user can paste into an issue, in three pieces. `DiagLog` installs a `qInstallMessageHandler` that **CHAINS** to the previous one (journald behaviour unchanged) and keeps the last 500 lines in a mutex-guarded ring. **Two-phase install, and the order is load-bearing**: `DiagLog::install()` is the FIRST statement of `main()` (before `QApplication`, before the helper dispatch, so QPA/QML-engine warnings are caught and a crash during construction still reports), but the FILE is opened only after this process has WON the single-instance handshake - every `return` above that point belongs to a process that forwarded its command to the running instance, and rotating the log from one of those would throw away the running instance's own file. Rotation is startup-only (`unisic.log` -> `unisic.log.1`, 0600 in `<AppDataLocation>/logs`), so exactly the two runs that matter for a crash report survive; `aboutToQuit` writes `=== clean exit ===`, and its ABSENCE is what lets the next start tell a crash from a SIGKILL/OOM. `CrashHandler` is a separate TU whose stated rule is **async-signal-safe calls only** - `write`/`open`/`raise`/`sigaction`/`backtrace`/`backtrace_symbols_fd` and nothing else (NOT `backtrace_symbols`, NOT `snprintf`, NOT `QString`); 64 KiB `sigaltstack` + `SA_ONSTACK` so a stack-overflow SEGV can still print, `backtrace()` warmed once at install so the unwinder's lazy `dlopen` is not attempted from a handler, `alarm(5)` so a wedged handler still dies, and it re-raises with `SIG_DFL` so systemd-coredump still gets a core. Compiled out under ASan/TSan. **Privacy is one choke point**: `DiagRedact::redact()` runs on EVERY line before it is stored, masking header/JSON/assignment-shaped secrets, URL userinfo and query strings, and shortening `$HOME` - because `destinations.json` holds live upload tokens and the user pastes this into a public tracker. `tests/DiagRedactTest.cpp` pins that contract. The two subprocess helpers keep NO file: they tag their lines to fd 2 and `AppContext` folds each helper's **stderr only** (stdout is their action protocol) into the one merged log.
- `src/theme/ThemeController` - module QML singleton (`QML_SINGLETON`) owning the selected theme (persisted `ui/theme`) and bridging the live system palette (`qApp->palette()` + `QStyleHints::colorScheme()`) for the "system" theme. `ThemeController::instance()` shares the one engine-created object with `IconImageProvider`. **Do NOT `qmlRegisterSingletonInstance` into the `Unisic` URI** - that clobbers the module's other C++ QML_ELEMENT types (e.g. `AnnotationCanvas` becomes "not a type"). **Community themes**: `<config dir>/themes/*.json` (schema = Theme.qml's `_defs` seed: 8 required colors + `isDark`, every `_expand()` token an optional override; parser `src/theme/ThemeJson.h`, header-only, unit-tested). **Built-in split**: core `system`/`unisic`/`dark`/`light` are hardcoded in Theme.qml's `_defs` (`unisic` is the mandatory palette AND the fallback for every unresolvable id - do not remove); the decorative palettes (Catppuccin ×2, Dracula, Nord, Gruvbox) are shipped as REAL editable JSON files: `resources/themes/*.json` lives in qrc only as the SEED SOURCE, and `ThemeController::seedThemesFolder()` copies them into `<config>/themes/` ONCE (guarded by the `ui/themesSeeded` flag - deleting a seeded file keeps it gone, never re-created; existing files never clobbered). They then load through the normal custom-theme scan as `custom:<stem>` ids. `ThemeJsonTest::shippedThemesAllParse` parses every shipped JSON from the source tree so a broken seed fails tests, never a user. Resolution order in Theme.qml `pal`: core → `custom:` (incl. seeded decoratives) → unisic fallback. ThemeController scans + hot-reloads via QFileSystemWatcher (dir AND files re-armed each scan - the watcher drops deleted paths), exposes `customThemes`/`customDefs`/`customThemeErrors`, ids are `"custom:<file-stem>"`; Theme.qml resolves them in `pal` with a stock-palette fallback when the file is gone (selection kept). Editing the ACTIVE custom theme bumps `rev` so provider icons recolor. Recording overlays are theme tokens too (`recBadge{Bg,Text}`/`recDot`/`countdown{Bg,Number}`/`keystroke{Bg,Text}`, deliberately NOT palette-derived - they sit over recorded content): RecordBorder.qml reads them directly; the keystroke painter gets them via `GifRecorder::setKeystrokeThemeProvider` (lazy - the recorder outlives engine construction order); the GNOME helper gets them as 5 trailing HexArgb argv colors (alpha matters for pill/disc).
- `src/theme/IconImageProvider` - `image://icon/<name>?color=%23RRGGBB&sz=NN&v=<rev>`. System theme → `QIcon::fromTheme` (Breeze fallback theme set in main), else the bundled monochrome SVG in `resources/icons/sym/` recolored via `CompositionMode_SourceIn`. Pixmap provider ⇒ `UIcon` must stay `asynchronous: false` (runs on GUI thread; `QIcon::fromTheme`/`qApp->palette()` aren't thread-safe).
- `qml/` - fully custom SwiftUI-like design system (**no Kirigami/Breeze**; QQuickStyle forced to "Basic"): `Theme.qml` singleton (9 palettes computed from tokens; keep property names stable - 19 files depend on them) + `ToolCatalog.qml` singleton (single source of annotation tools **and their letter shortcuts**; both toolbars build from `visibleFor(ctx, hiddenTools)`, both keyboard hosts resolve through `toolForShortcut()`) + `components/` (UButton, USwitch, UIcon, UComboBox, …). **Four kit singletons own the cross-cutting rules, and each is the ONLY copy of its rule** - extend them, never write a rival: `UKeys` (keyboard activation: a dedicated `Keys.on<Key>Pressed` runs BEFORE `Keys.onPressed`, ignores modifiers and arrives pre-accepted, so an unguarded handler swallows the window's own chords - `UKeys.activate/claim/unmodified` hand a chord back to the bubbling path, KeypadModifier masked so numpad Enter still acts), `UFlyout` (containment: every dropdown/menu/picker is parented to its ANCHOR, not `Overlay.overlay` - Qt's positioner then tracks the anchor, the window and every ancestor, `margins` clamps, and the kit adds only what Qt does not do, namely flip-above and shrink-to-fit-with-internal-scroll; a flyout never covers its own field), `UNameBridge` (a row caption becomes the control's accessible NAME when it is alone in the row and its DESCRIPTION when several share it - one caption is one identity), `UFocusRing` (the ring, plus THE INSET RULE). `FocusScroll` is the fourth member of the `MiddleScroll`/`WheelBoost` family: a plain Flickable is not a ScrollView, so Tab could land on a control far below the fold with `contentY` untouched; it reveals only items COMPLETELY off screen, because a click is a focus change too and scrolling a partly visible control into view would move the page under the pointer that clicked it. Icons are `iconName` (freedesktop names) via `UIcon`, not emoji. Windows are created from C++ via QQmlComponent with per-window QQmlContext (`editorSession`, `overlayController` context properties). Layout rules that are load-bearing, not taste: nothing may move or appear under the pointer (colour feedback only), a control never toggles `visible` in a row (it stays and disables, or the row reflows), every option is a `USettingRow` bordered card on ONE full-width grid, and the main pages must still fit above the fold at 1060×700, which is why the Capture tiles are 140 px tall and its option grid is exactly 8 cells (delay / repeat last region / upload server + the five after-capture toggles); a ninth strands itself on a fifth row AND overflows the fold.
- **Accessibility contract** (kit components + app QML): Tab walks the interface, the focused control draws a `UFocusRing` in the accent colour, Space/Enter activates, and every control carries `Accessible.role/name` plus its state. Composite items name themselves ONCE: the container gets the assembled name and each label inside sets `Accessible.ignored: true` (ignoring the Column instead only promotes its children). Two places are deliberately OUT of the tab chain and must stay out: **history tiles** (the `GridView` owns keyboard navigation through `currentIndex` + its own `Keys` handler; a per-tile tab stop would make Tab walk a hundred captures and move a different cursor than the ring shows; AT-SPI still enumerates and Presses them), and the **capture overlay's** toolbar (`focusable: false` / `activeFocusOnTab: false` on every chip and button): there Space/Enter mean "confirm the capture" and the overlay holds an exclusive keyboard grab, so a focused chip would swallow the gesture that finishes the shot. The overlay keeps its own vocabulary instead: the tool letters from `ToolCatalog`, Space/Enter to confirm, Escape to cancel. Key handlers on focusable items are `Keys.onSpacePressed`/`onReturnPressed`/`onEnterPressed`, never a blanket `Keys.onPressed`, or a focused tile eats the window's `Ctrl+1`…`Ctrl+6`/`Ctrl+V`.

Recording: one `GifRecorder` parameterized by `Output{Gif,Mp4,WebM}` + `SourceType{Screen,Region,Window}`; Window source passes `types=WINDOW` to `ScreenCastSession` (portal window picker). GIF (region/screen) and video (screen/region/window → MP4/WebM) keep separate `AppContext` entry points but share ONE page: `RecordPage.qml` hosts both behind a Video/GIF segment and `GifPage.qml` is gone. Which half is showing is a persisted setting (`Settings::recordPageMode`, key `ui/recordMode`), never page state: every page lives behind a `Loader` that is destroyed on navigation, so a mode kept in the page would reset the moment you walk away from it. The Screen/Region/Window buttons keep their places across the flip and only enable/disable (GIF has no window source, and the labels deliberately do not change, because swapping them would reflow the row); what the button will produce lives in its spoken description instead. So the sidebar is five entries (Capture, Record, Edit, History, Servers) plus the Settings gear in the bottom app card, page shortcuts `Ctrl+1`…`Ctrl+6` (6 = Settings, same as `Ctrl+,`). Recording overlays: `CursorOverlayPainter` (pointer/halo/ripples, only in CursorMetadata mode) and `KeystrokeOverlayPainter` (screenkey-style badge, `record/keystrokes`, works in EVERY cursor mode) both composite in `compositeCursorOverlay` into the reused scratch buffer - `m_lastFrame` stays clean (it is the sample-and-hold source; baking a badge in would freeze it on held frames). Key/click events come from `KeyCapture`/`ClickCapture` (libinput udev observers on their own threads, plain open no grab, `HAVE_LIBINPUT`, gated on `InputPermission::probe()` - needs the `input` group, degrades silently). Badge labels are PHYSICAL (US) key legends: evdev codes only, the compositor's xkb layout is not observable from a libinput observer. Global hotkeys: `GlobalHotkeys::defineAction` registers with KGlobalAccel flag `IsDefault(0x8)` only (preserves KCM edits; a separate `SetPresent(0x2)` call *clears* the binding on that daemon). **The IsDefault reply lies**: when the daemon has an active binding stored as "none" it echoes the requested keys while filling only the default column - the action stays dead. So `AppContext::defineHotkeys` runs `hotkeyBindStatus` on EVERY launch: real `shortcutKeys` queries; any action reported unbound while the app stores a key gets re-asserted via `setShortcut` (`SetPresent|NoAutoloading`, 0x6); a differing bound key is synced into the UI. A deliberate KCM unbind made while the app runs still sticks (the change signal empties the stored string). User edits/imports also push `setShortcut`. **Alternate hotkeys**: each action holds up to 4 bindings - stored as ONE comma-joined portable string ("Meta+Shift+S, Print"; QKeySequence chord limit), `keysFor` flattens the chords into the daemon's alternate-key list, `UShortcutList` (chips + "+ add key" recorder) edits it. The daemon REORDERS alternates in replies - every binding comparison must go through `GlobalHotkeys::sameBinding` (set-based), or reorders read as KCM edits/failures. **Non-KDE hotkeys** go through `PortalGlobalShortcuts` (org.freedesktop.portal.GlobalShortcuts): the portal pins app identity PER D-BUS CONNECTION at its first portal call, and on GNOME Qt's portal platform theme touches the Settings portal during QGuiApplication construction - the shared bus is already pinned to app id "" for terminal/AppImage launches, and gnome-control-center's shortcuts provider silently DISCARDS BindShortcuts from an empty app id (code 2 → hotkey UI collapses to the compositor-binds card). So ALL GlobalShortcuts traffic runs on a private bus connection whose first call is `Registry.Register` (re-issued after a portal restart - the association is in-memory portal-side). GNOME also enforces the spec's one-BindShortcuts-per-session; re-binds ride the fresh-session retry. `UNISIC_HOTKEY_BACKEND=portal` forces this path on a KDE box for testing.

Deliberate choices: keep working via portals on non-KDE; clipboard mirrored through `wl-copy` when present (Wayland reliability); recording region = full-monitor stream cropped in ffmpeg (portals can't select regions). **Multi-monitor recording target**: the SYSTEM share dialog is the screen selector - do not add an app-side picker in front of it (tried in dev, rejected: it duplicates the portal's own monitor choice). The dual-monitor bug was the restore token suppressing that dialog while silently replaying an old share - including an "entire workspace" one, which recorded BOTH screens with no dialog to say otherwise. Fix in `GifRecorder::openPortalSession`: full-screen/replay recordings (`Screen` source) on a multi-monitor setup never SEND the stored token, so the portal dialog always appears and the user's pick there is authoritative; with one monitor the token keeps its silent-start convenience. Region recordings keep per-monitor tokens (`record/portalRestoreTokenMonitor@<name>`) and `onStreamReady` verifies the delivered stream with `StreamGeometry::streamMatchesScreen` (header-only, unit-tested in `tests/StreamGeometryTest.cpp`): position must match the target screen's top-left AND the size must not be a workspace stream (whose position equals a primary-monitor target, so size has to be checked too); the one legitimate mismatch - GNOME fractional scaling streaming the logical size - is recognized as a UNIFORM rescale that isn't the workspace union. On mismatch the token is wiped and the portal reopened once (picker shows), then it fails with an actionable message.

Clipboard history (KDE Plasma): `AppContext::copyImageToClipboard` - on Plasma/KWin (`org.kde.KWin` on the bus) images are re-asserted through **`KSystemClipboard`** (KF6::GuiAddons, optional `HAVE_KGUIADDONS`) with an empty **`x-kde-force-image-copy`** marker MIME attached (`makeForceImageMime`). Without that hint Klipper leaves the capture pasteable-now but never copies it into clipboard **history**, so the shot vanishes as soon as anything else is copied (issue #51). `QClipboard::setImage`/`wl-copy` advertise only `image/png` and cannot attach an empty marker; `KSystemClipboard` sets the whole `QMimeData` over the wlr data-control protocol, which also lands **without a focused window** - so the KDE branch skips the `wl-copy` mirror entirely (it bumps `m_clipboardSeq` so a stale deferred mirror can't clobber it). Spectacle/Flameshot do exactly this. Verified empirically: with the hint the image persists in the selection after the setter process exits (Klipper now owns/serves it, adding its own `application/x-kde-onlyReplaceEmpty`); without it, the selection reverts to the previous entry. The plain `QClipboard::setImage` still runs first so synchronous local reads (X11, the smoke test) keep working. Fix guarded by `clipboardHistoryHintCheck()` in the F8 smoke test + a **Klipper clipboard history** Developer button.

After-capture pipeline: every enabled action (copy/save/upload/editor) fires independently and immediately in `AppContext::finishCapture` - the editor never blocks the others. Two extra post-capture affordances live here too: (a) **copy last capture** - a regular always-registered hotkey (`copy-last`, default Meta+Shift+C, `hotkeys/copyLast`): `finishCapture` retains the newest screenshot PNG-encoded off-thread (`m_lastCaptureData`, megabytes not a pinned QImage) and `copyLastCapture()` decodes + copies on demand. This REPLACED the 2s global Ctrl+C grab (it stole ordinary copies right after a capture); startup still releases AND unregisters the legacy `quick-copy` action so upgraded installs can't keep a stale Ctrl+C grab or a phantom KCM row. Spectacle-parity in-window Ctrl+C: the region overlay (`OverlayController::confirmAndCopy` + `takeCopyRequested`, screenshot flow only) confirms the selection and forces a clipboard copy even with auto-copy off, and the editor's Ctrl+C copies the composited image. (b) **floating preview** - clicking a capture-notification thumbnail calls `CaptureNotification::preview()` → `AppContext::openPreview` which dumps the full image to a temp PNG and opens `PreviewWindow.qml` with a `PreviewController`. With layer-shell the surface is FULLSCREEN with the wl input region masked to the visible card (`setInputRect`, same pattern as the capture popup) so the card drags as a plain QML item - the only smooth option, layer surfaces can't be system-moved and per-event margin repositioning diverges; pin toggles overlay/top layer. Fallback: normal frameless window + `startSystemMove` + stays-on-top hint. Opacity slider fades the card item (NOT `Window.opacity` - qtwayland silently ignores it). Bringing a file the OTHER way (in, not out) runs through one router: `AppContext::openPath()` (image → editor, recording → trim window, anything else → a toast) is what the Edit page's file dialog, the main window's `DropArea` (`openDroppedUrls`/`openImageData`) and Ctrl+V (`pasteFromClipboard` → `pasteMimeData`) all end in, so there is exactly one routing rule and no payload can land silently. What the file IS decides, never what the drag source or dialog filter claimed. A dropped/opened FILE keeps its path as the editor's `overwritePath` (Ctrl+S writes the original), pasted PIXELS deliberately do not (no file of their own → Ctrl+S saves a new capture). Remote urls are refused, never downloaded: a browser drag that only offers an http url gets a message; one that offers real `image/*` bytes goes through `openImageData`. The drop target lives at the WINDOW level (a page-level one would die with its `Loader`) and is a `DropArea`, which takes drag events only, so nothing below it stops being clickable. `pasteMimeData(const QMimeData *)` is split out of `pasteFromClipboard()` precisely so the dev check can exercise the routing without writing to the system clipboard: a check that clobbers what the user had copied is a bug, and a snapshot/restore of `QClipboard::mimeData()` cannot be faithful (delayed-rendering formats, plus a re-assert would duplicate the entry in Klipper's history). Filenames come from `AppContext::makeFileName()` (template tokens `%date% %time% %datetime% %unix% %rand%`, format/quality from settings). Settings export/import (`AppContext::exportSettings/importSettings`) serializes all `Settings` Q_PROPERTYs via the metaobject (not raw QSettings keys - those omit defaults) plus destinations. Settings keys: NEVER put a key in a QSettings group named "general"/"General" - that name collides with INI's magic General section (serializes `[%General]`, parses back as `"General/..."`, case-sensitive reads miss → resets to defaults every launch). General-tab settings are top-level bare keys (plain `[General]` section) for exactly this reason. CLI: `unisic --fullscreen|--region|--window|--measure|--monitor|--recapture|--gif|--export-settings <f>|--import-settings <f>`. `--monitor` = screen under the cursor (`CaptureManager::captureActiveScreen`: KWin `CaptureActiveScreen` resolves the pointer's screen compositor-side; elsewhere the `QCursor::pos()` hint + portal workspace crop). `--recapture` = repeat the last region shot: the overlay stores each confirmed selection as `capture/lastRegion` (`"<screen>|<x>,<y>,<w>,<h>"` in LOGICAL px of the named screen - survives the KWin-native vs portal-scaled freeze difference), `recaptureLastRegion()` re-captures that screen and crops after rescaling to the current image size.

Developer mode: a `UNISIC_DEV_BUILD` CMake flag (auto ON for local builds - i.e. `UNISIC_BUILD == "dev"` - OFF for CI releases) exposes a **Developer tab** in Settings (`App.devBuild`). A dev build is also a **fully separate app** from installed stable: app name `unisic-dev` (which moves all QStandardPaths: cache, history, U-2-Net model), desktop id `app.unisic.UnisicDev`, own single-instance socket, own config dir `~/.config/unisic-dev` (seeded from stable on first run with all hotkeys UNBOUND - the stable KGlobalAccel component still owns its keys) and own hotkey component `unisic-dev`; the tray icon gets an amber corner dot. `ensureDesktopFile()` writes the dev entry and removes the legacy dev-written shadow of `app.unisic.Unisic.desktop` in `~/.local/share/applications` (which used to hijack the stable menu entry). Both apps can run and be CLI-targeted side by side. It shows detected compositor capabilities (`App.capNativeNotification/capCustomNotification/capRecordBorder`), a full smoke test bound to **F8** (`AppContext::runSmokeTest`), and a **per-action button** for each path. **REQUIREMENT for every new user-facing feature/path: wire it into BOTH** (a) the sequential smoke test in `AppContext::runSmokeTest` (as a pass/fail/skip step) **and** (b) a dedicated per-action button in the SettingsPage Developer pane (reuse the public `Q_INVOKABLE`, or add a small `devTest*()` for non-capture paths). This keeps the dev harness an exhaustive, hand-checkable inventory of what the app can do. In a release build, capability-gated options are shown greyed-out with an explanation rather than hidden.

## Internationalization (REQUIREMENT)

Every user-facing string MUST be wrapped in `qsTr()` (QML) / `tr()` (C++) **and** translated in all five `i18n/unisic_{en,pl,es,it,fr}.ts` files. English is the source language - its `.ts` mirrors the source text (translation == source). Workflow for any new/changed string: (1) add the `qsTr`/`tr` call; (2) run `cmake --build build --target update_translations` - lupdate rescans C++ + `qml/*.qml` and appends the new strings as `type="unfinished"` with an empty `<translation>`; (3) fill every unfinished `<translation>` in **all five** files and drop the `unfinished` marker. A plain `cmake --build build` runs lrelease and bakes the `.qm` into the qrc (`HAVE_TRANSLATIONS`), so any `unfinished`/empty entry silently falls back to English at runtime - do not ship those. Keep placeholders (`%1`), filename tokens (`%date%`), file globs (`*.png`), and program names (`pw-play`/`paplay`/`aplay`) verbatim; match the per-language sound-cue convention already in the files (Shutter → Migawka / Obturador / Otturatore, Beep → Bip / Pitido / Bip, Off → Wyłącz / Desactivado / Spento, …). New QML component files must be added to `qt_add_qml_module` in `CMakeLists.txt` so lupdate scans them.

## What Unisic Is

Unisic is a planned screenshot and screen-recording tool for **Linux Wayland**, prioritizing KDE Plasma/KWin but portable via xdg-desktop-portal. Tech stack: **C++17+ with Qt 6, Qt Quick/QML UI**.

Required features (in rough build-priority order):

1. **Capture**: full screen (multi-monitor), interactive region (live selection with dimension readout), specific window.
2. **On-overlay annotation** during region selection (arrows, shapes, text) *before* the capture is finalized.
3. **Post-capture editor** auto-opened after every capture: arrows, lines, rectangles, ellipses, freehand, text, blur/pixelate, crop, numbered step markers, highlight, undo/redo.
4. **Modular upload destinations** (custom HTTP/FTP/SFTP/API + public services), auto-copy URL to clipboard, upload history.
5. **GIF screen recording** (distinct from normal video recording): record region/full screen, convert to .gif via ffmpeg; options for FPS, area, max duration.

Lower priority: tray icon + quick menu, configurable global hotkeys per capture mode, capture history with thumbnails.

## Hard Constraints

- **Wayland-legit capture paths only**: xdg-desktop-portal Screenshot/ScreenCast, KWin `org.kde.KWin.ScreenShot2` DBus API as a KDE-specific enhancement, PipeWire as the video backend, KGlobalAccel over DBus for global shortcuts, `QDBusInterface`/`QDBusConnection` for DBus. No X11-only capture hacks.
- **Mandatory UI palette**: Primary `#17153B` (main window/panel backgrounds), Secondary `#2E236C` and Tertiary `#433D8B` (secondary elements, hover/active), Accent `#C8ACD6` (action buttons, attention).
