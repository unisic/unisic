# Architecture: `src/` subsystems

Read the bullet for a subsystem before changing it. Every claim here is a fix that already cost a debugging session.

- `src/AppContext.*` - facade exposed to QML as context property `App`; owns all subsystems and the after-capture pipeline (editor/save/clipboard/upload/history), tray icon, hotkey dispatch.
- **Still GIF (`gif` as a fourth image format) goes through ffmpeg, never through Qt.** Verified on Qt 6.11.1: `QImageWriter::supportedImageFormats()` lists NO gif (the bundled plugin reads and never writes), while `QImageReader`'s does - so a `QImage::save(..., "GIF")` fails silently-ish and there is no Qt-side fix to look for. `FfmpegUtil::encodeStillGif(QImage, quality)` (kit submodule, `external/unisic-kit/src/media/FfmpegUtil.*`) pipes the frame in as PNG on stdin and reads GIF bytes off stdout, both palette passes in ONE filter graph (`split[a][b];[a]palettegen=max_colors=N[p];[b][p]paletteuse=dither=D:alpha_threshold=128`) - correct only because a single frame IS the whole palettegen buffer; the recorder must keep its two-pass form or palettegen buffers a whole recording into RAM. It is BLOCKING by design (~0.5 s for 3840x2160, measured, same order as the PNG encode it replaces) because it stands in for `QImage::save()` inside the synchronous `saveImageTo`. `alpha_threshold=128` keeps GIF's one transparent entry; without it a transparent capture composites onto black. **Quality maps to palette size, and the low end must NOT dither**: dither noise is exactly what LZW cannot compress, so on a 4K frame 64 colours cost 287 kB undithered but 312 kB with `sierra2_4a`, against 386/416 kB at 256 - a dithered low end makes the "smaller" setting produce the BIGGER file. Hence 64/none, 128/bayer_scale=5, 256/sierra2_4a, pinned by `qualityBuysColors` in `tests/StillGifTest.cpp`. In `AppContext::saveImageTo` the encode runs BEFORE the collision-dedup loop, for the same reason the transparency auto-switch does: a failed encode (no ffmpeg) rewrites the name to `.png` with a toast, and the loop has to de-duplicate the name that is actually written - the file must never lie about its bytes. `editableKindFor` splits `.gif` by `QImageReader::imageCount()` (header-only, measured 0 ms): 1 frame → image editor, more → trim window, -1 (missing file) → the old answer. `AppContext::ffmpegAvailable` (CONSTANT, cached `findExecutable`) greys out both "Save as GIF" entries; `convertFileTo(path, format)` is the reusable rewrite-beside-the-original primitive behind the History tile. F8 line and Developer button: `staticGifCheck()`/`devTestStaticGif()`.
- **One encoder, one policy: `src/ImageEncode.*`.** Every QImage-to-bytes path in the app goes through `ImageEncode::encode(img, format, quality)` - `saveImageTo`, `encodeImageAsync` (clipboard + upload), `overwriteImageFile`, `autoConvertIfLarge`. It returns the bytes, the format they ACTUALLY are, the mime type, and a `fallbackReason` token when those two disagree with what was asked. The token (`"alpha"`, `"gif"`, `"encoder"`) is deliberately not a sentence: the wording stays with the other `tr()` strings in AppContext, so `ImageEncode` needs no translations and links into `tests/ImageConvertTest.cpp` with only Qt6::Gui and FfmpegUtil. Three substitutions are possible and all of them land on PNG: JPEG cannot hold alpha (`hasTransparency`, the ≤256x256 sampled scan - a transparent REGION is always caught, a single stray pixel in a 4K frame need not be), GIF needs an ffmpeg that may be absent, and WebP tops out at 16383 px per side, which a stitched multi-monitor capture really can exceed. **The caller must rename after encoding, never before**: `FilenameTemplate::withExtension(name, enc.format)` in `saveImageTo` runs before the collision-dedup loop, or two transparent `.jpg` saves in the same second both pass the `.jpg` existence check and overwrite each other's `.png`. Cost: the bytes are a second copy of the picture (~5-10 MB for a 4K PNG beside its 33 MB of pixels), freed at the write.
- **The four automatic conversions, and what each one is forbidden from doing.** (1) Incoming files - `EditorSession::save()` under `convertIncoming`: a file opened from disk (drop, paste, Open, history Edit) leaves as a NEW file in the settings format, never an in-place rewrite, because the extension would then disagree with the bytes and a lossy re-encode would land on someone's only copy. Pixels with no source file (Ctrl+V, a dropped payload) already take the `saveImageAuto` path and need no rule. (2) Over-size - `AppContext::autoConvertIfLarge`, called at the END of `saveImageTo` so it measures the real file, and BEFORE `openAfterSave` so what opens is the file that survived. It refuses whenever `!enc.ok() || enc.format != target || enc.bytes.size() >= size`: a rule whose whole point is a smaller file must never produce a larger one, and a flat-colour screenshot re-encoded to PNG absolutely can. It writes the new file first and removes the original only after a flushed, size-checked write, so a failure can never leave neither. (3) Upload format - `uploadImageFormat()` ("" and "same" both mean "leave it alone") is threaded through all four upload sites: `uploadImage`, the `finishCapture` upload branch, `uploadFromNotification` and `uploadFromHistory`. The first three re-encode the in-memory image; the history one re-reads the file and is guarded by `editableKindFor(path) == "image"`, so recordings and animated GIFs go up untouched on the raw `uploadFile` path. Nothing on disk or in history is rewritten - only the bytes being sent. (4) Manual - the History tile's `Convert to *` entries and `EditorSession::saveAs`, both of which pass `allowAutoConvert=false` into `saveImageTo`: an automatic rule must not undo a format the user just clicked. F8 line and Developer button: `imageConvertCheck()`/`devTestImageConvert()`; unit test `tests/ImageConvertTest.cpp` (magic numbers, not extensions).
- **Watermark patterns: one stamp built once, blitted N times.** `UnisicImageEffects::watermarkText/watermarkImage` (`src/editor/ImageEffects.*`) take a `pattern` on top of `position`: `"single"`, `"tile"`, `"diagonal"`, `"corners"`, `"band"`, anything else reading as `"single"` so a hand-edited config cannot produce an unwatermarked capture. **The text is laid out ONCE even for a tiled pattern** - this runs synchronously on the after-capture path, before save/clipboard/upload/history/editor all read the same frame, and a few hundred `QPainter::drawText` layouts at 4K is a visible stall where a few hundred small alpha blits is not. `tile()` therefore takes a prepared QImage and only positions it (stepX = 1.8w, stepY = 3.0h, odd rows offset half a step so the grid reads as a watermark and not as a table). **The blit count is capped at `kMaxStamps = 1024` by GROWING the spacing, not by stopping early**: a pathological stamp (one character at the minimum font, a 1x1 logo) would otherwise blit unbounded, and truncating instead of respacing leaves a visibly half-finished pattern. `"diagonal"` rotates about the centre and tiles the square on the image's DIAGONAL, not its rect - anything smaller leaves bare triangles in the corners. Stamp size is per pattern (`textPixelSize`/`logoMaxSide`) rather than one size scaled: `"band"` is rendered large instead of upscaled from a small stamp, which would be soft. `position` is honoured by `"single"` only, which is why the Settings Position row greys out for the rest. Opacity is applied once at blit time so it dims the mark as a whole, not the glyphs and their drop shadow separately. F8 line and Developer button: `watermarkCheck()`/`devTestWatermark()` (all five patterns, plus tile-covers-more-than-single); unit tests `watermarkPatternsCoverTheirOwnArea` and `watermarkSizeScalesTheStamp` in `tests/AnnotationCanvasTest.cpp` count changed pixels rather than pinning an exact rendering. The `watermarkScale` setting is a percent applied AFTER each pattern's own clamps, so 100 is bit-for-bit the pre-setting rendering and no existing user's watermark moved; `applyScale` then hard-bounds the result (2000 px font, 8192 px logo) so a hand-edited config cannot allocate a stamp larger than the capture. **Covered area is NOT monotonic in scale for `"diagonal"`** (measured 8888/9471/8061 at 50/100/200 on a 400x260 frame): tile spacing is a multiple of the stamp, so density is scale-invariant by construction, and the rotation then decides how much of each edge stamp falls outside the frame. The test asserts monotonicity for the other four and only difference for that one - do not "fix" it by asserting growth.
- **The Settings watermark preview cannot lie, by construction.** `AppContext::stampWatermark(QImage)` is the ONE place the watermark settings are read; `finishCapture` calls it and so does `WatermarkPreviewProvider` (`src/editor/WatermarkPreview.*`, registered in `main.cpp` as `image://watermark/`). A logo type with no file loaded falls back to the text stamp there - "watermark on" must never silently mean "watermark off". The mock capture (`UnisicImageEffects::mockCapture`) is painted in C++ from the app palette rather than assembled from Theme tokens in QML because it is picture CONTENT, not a UI surface, and the stamping code takes a QImage; it carries a light half AND a dark half on purpose, since opacity and size are exactly the settings that decide whether a mark survives over one but not the other. It lives in `ImageEffects.cpp`, not next to the provider, for one reason: that TU is already linked into `unisic_annotation_canvas_test`, so `mockCaptureCarriesLightAndDarkAreas` can pin the light/dark floors and the degenerate-size clamps, while `WatermarkPreview.cpp` pulls in `AppContext.h` and cannot be linked into a light test target. QML caches a provider image by URL, so `App.watermarkPreviewSource` carries a revision bumped by all eight watermark settings and the `Image` sets `cache: false` - without both, the preview freezes on its first render, or one drag of the opacity slider grows the pixmap cache for the session. Nothing is cached provider-side: re-rendering one ~460 kB frame is cheaper than invalidating a cache against eight settings. F8 line and Developer button: `watermarkPreviewCheck()`/`devTestWatermarkPreview()` - the check goes through `requestImage` itself, including the no-`sourceSize` fallback, not just the pipeline step behind it.

- `src/diag/SmokeTests.cpp` - **the second translation unit of the SAME `AppContext` class**, not a separate object: every `devTest*` action behind a button in the Settings Developer pane, every `*Check()` those actions share with the F8 smoke test, `smokeLog()` and `runSmokeTest()` live here. `AppContext.cpp` was one 9300-line file and the diagnostics were a third of it. A new self-test is still declared in `AppContext.h` next to its neighbours; it is DEFINED here, never back in `AppContext.cpp`. Helpers both halves use (`devTestImage`, `ocrBoxTestImage`, `qrPreviewImage`, `bundledSoundIds`, `makeForceImageMime`, `kwinScreencastProbe`, `kSelfHideSettleMs`) lost their `static` and are declared in `src/diag/SmokeSupport.h`; a helper only the tests use stays a file-static in `SmokeTests.cpp`. Both files carry the same include block with the same `#if` guards, so a new optional dependency has to be added to both.
- **The installed `.desktop` `Exec` must be an ABSOLUTE path** (`resources/app.unisic.Unisic.desktop.in` + `UNISIC_DESKTOP_EXEC`, configured from `CMAKE_INSTALL_FULL_BINDIR`). KWin authorizes a caller for its restricted interfaces by comparing `QFileInfo(splitCommand(Exec).first()).canonicalFilePath()` against `/proc/<pid>/exe`; a bare `unisic` resolves against KWIN's working directory, matches nothing, and `canonicalFilePath()` returns `""`, which can never equal `/usr/bin/unisic`. Up to 0.7.5 the installed file said `Exec=unisic`, so `org.kde.KWin.ScreenShot2` was refused on EVERY native package and silently fell back to the portal - invisible in development, where `ensureDesktopFile()` writes an absolute `applicationFilePath()`. Spectacle, krfb-virtualmonitor and xdg-desktop-portal-kde all install absolute Execs for the same reason. The AppImage job pins it back to the bare name on purpose (relocatable AppDir, and a transient FUSE mount can never satisfy the check anyway).
- `src/capture/` - backends: `KWinScreenShot2` (silent, needs the installed .desktop file's `X-KDE-DBUS-Restricted-Interfaces`; auto-falls back on auth failure) and `PortalScreenshot`; `PortalRequest` implements the portal Request/Response handle pattern; `ScreenCastSession` drives the ScreenCast portal for recording; `CaptureManager` picks the backend.
- `src/editor/AnnotationCanvas` - the core drawing surface (QQuickPaintedItem): all tools, selection, undo/redo, and final compositing in **image-pixel space** (DPR forced to 1.0). Used by both the overlay and the editor; export is exactly what's rendered.
- `src/overlay/OverlayController` - freezes each screen (one capture per monitor), spawns one fullscreen `OverlayWindow.qml` per screen, returns annotated crop (screenshots) or physical-pixel region (GIF). **The caller names the session's purpose** (`Purpose::{Shot,Measure,Ocr,Gif,Video}`, an argument of both funnels, reaching QML as the `overlayPurpose` context property next to `annotationToolsEnabled`): the two funnels each serve several modes, so the window cannot deduce which one opened it, and until it was told, all five froze the screen and drew identical chrome - a mis-fired hotkey only announced itself once the shot was taken or the recording had started (issue #98). The overlay spends it on the mode badge, the screen-edge frame, the selection tint (`AnnotationCanvas.uiAccent`, no C++ painting change), the confirm button's wording and the canvas's spoken name. Only the badge and the frame are behind `Settings::overlayModeBadge`, and `Settings::overlayModeStyle` picks HOW the mode is named once it is on - `badge` (the named pill) or `icon` (one 35%-opacity mode glyph in the middle of the screen, drawn by `UModeGlyph` with the selection CUT OUT of it, so the part being framed over is not drawn and the rest still names the capture - hiding the whole glyph on contact made it vanish as soon as a selection touched one corner, user-reported). The coloured frame belongs to neither style: it is the mode's colour, not one of the two ways of naming it. A button that names the wrong action is a bug, not a preference, so the wording is not gated. `purposeName()` is a plain string, not a Q_ENUM, because OverlayController reaches QML as a context property rather than a registered type - `overlayModeCheck()` (F8 step, Developer pane button) pins each name against the literal `OverlayWindow.qml` switches on, since a typo on either side silently reads as a screenshot over a running recording. **Smart pick and U-2-Net background removal were REMOVED in 0.7.1b** - do not reintroduce without asking. `src/overlay/ObjectDetector.*` (pure-pixel line-pair/flood-fill/enclosed-interior detection driving a click-to-pick region overlay), `src/segment/U2NetSegmenter.*`, the whole `HAVE_ONNX`/onnxruntime CMake path, the editor's "Remove background" action and the Settings model-download UI are all gone: the detector never matched real windows reliably enough to ship on (it was EXPERIMENTAL, default OFF), and no packaging channel ever built onnxruntime in, so `HAVE_ONNX` was OFF in every shipped package - U-2-Net only ever ran in local dev builds. `AnnotationCanvas::Tool` keeps `ObjectPick = 13` as a RESERVED hole so the persisted enum values of the tools after it do not shift. The editor's smart eraser (`SmartErase = 12`) is unrelated and stays: it rebuilds the background under the stroke from the four boundary strips just OUTSIDE the rect (never from inside it - the object is in there). Each strip sample is the per-channel median of a 5-along × 3-out window; then the strips are CLEANED - ring median + 3·1.4826·MAD band marks outliers, which are re-interpolated from the inliers bracketing them - and only then interpolated as a **Coons patch**, clamped per pixel to the range of the four samples it interpolates. Computed at ≤192² and rescaled (smooth by construction, so the rescale is free); reuses Blur's `fxPatch` cache + `m_fxFast` drag rule; samples via `pixelColor` (converting a 4K base per drag move would rewrite ~33 MB). **Every one of those steps is load-bearing, do not simplify them away**: up to 0.7 it filled with ONE averaged colour sampled from the rect's OWN border, which read as a smudge; a plain Coons over raw strips then smeared the object across the patch whenever a stroke edge cut through it (the normal case - scrubbing over text) and overshot into bright bands. `tests/AnnotationCanvasTest.cpp` pins all three: `smartEraseFollowsGradientBackground` (flat fill → drift 41/255), `smartEraseOverlappingStrokesStayOnBackground` (no outlier rejection → drift 210/255), `smartEraseRebuildsFlatBackground`.
- `src/record/` - `PipeWireGrabber` (libpipewire thread, keeps latest SHM frame) → `GifRecorder` samples at fixed FPS into ffmpeg stdin (lossless x264rgb temp), then two-pass palettegen/paletteuse GIF conversion. `RecordBorderHelper` - the GNOME record-region frame: mutter has no layer-shell and no keep-above for xdg_toplevel, so `unisic --record-border-helper` (dispatched in main() BEFORE QApplication - must boot on xcb, and one process can't host two QPA platforms) draws an XWayland **override-redirect** window (mutter's topmost stacking layer, click-through via `WindowTransparentForInput`). The region travels as monitor FRACTIONS: XWayland renames RandR outputs (`XWAYLAND<n>`) and its coordinate space (logical vs physical layout mode) need not match the Wayland one, but the fraction of the monitor is invariant; the helper pads 2 px outward so rounding can never bleed the frame into the ffmpeg crop. Helper lifetime = parent's stdin pipe (EOF → quit - a crashed parent can't orphan the frame). `UNISIC_RECORD_BORDER=helper` forces this path on KDE for testing; `capRecordBorder()` = layer-shell ∨ X11 session ∨ KWin ∨ `$DISPLAY`.
- `src/upload/UploadManager` - destinations from `~/.config/unisic/destinations.json` (.sxcu-like; `$text$`/`$json:path$`/`$regex:$` extraction); `type: "curl"` shells out to curl for FTP/SFTP **and for any host whose upload is a plain PUT**. Three things make that second kind work, all optional and all off by default: `%file%` anywhere in `requestUrl` is replaced by the percent-encoded file name (`curlTargetUrl()`; with no token the name is appended, which is what an FTP directory wants, and either way `sanitizeFileName()` means the name cannot climb out of the target directory); `headers` are passed through curl's **stdin config**, never argv, exactly like `user`, because an API key is as much a secret as a password and `/proc/<pid>/cmdline` is world-readable for the whole transfer; and `urlPath`/`deletionUrlPath` resolve against curl's **stdout** through the same `extractUrl()` the http path uses, so a host that answers with the link (or with an id to build one from) is usable - without one the link is still `publicUrlBase` + name. That is the whole of the `buzzheavier.com` builtin: `PUT https://w.buzzheavier.com/%file%`, `urlPath: https://buzzheavier.com/$json:data.id$`, no account and no key. `tests/UploadUrlTest.cpp` covers the target composition and the response template offline, plus a live end-to-end upload that is skipped unless `UNISIC_LIVE_UPLOAD=1`. **Never compile an Imgur Client-ID in**: it identifies the *application*, so one shipped ID puts every user on one ~1250/day cap and makes whoever registered it answerable to Imgur for strangers' uploads. The builtin ships with no Authorization header; the user pastes their own ID (DestinationsPage swaps the raw headers-JSON field for a Client-ID field on any `api.imgur.com` destination), `startUpload` refuses an ID-less Imgur upload with an actionable message (Imgur itself answers a bare 429), and `ensureBuiltins` strips the placeholder ID that shipped up to 0.7 from stored configs. **Test upload** (the server editor's button) is `testDestination(QVariantMap)` → `testFinished(ok, url, error)`: it takes the UNSAVED form state and pushes a generated 64² checkerboard PNG (the palette's Secondary/Accent, named constants at the top of the .cpp) through the same http/curl transport a real capture uses. It resolves the destination OBJECT and calls `startUploadTo`; passing a *name* would be wrong, because `destinationNamed()` silently falls back to the first stored destination for an unknown name, so an unsaved config would be "tested" against somebody else's server. Nothing is persisted: no `destinations.json` write, no history entry, no clipboard touch. A curl test really writes `unisic-test.png` to the user's own server and Unisic cannot delete it again, which the sheet says out loud before they press it.
- `src/history/HistoryStore` - the model itself stays a plain newest-first list; `src/history/HistoryFilterModel` (QSortFilterProxyModel, `QML_ELEMENT`) is the History page's search/filter layer (`searchText`, `kindFilter`, `favoritesOnly`, `uploadedOnly`). `kindFilter` matches `CategoryRole` (`"image"|"gif"|"video"|"replay"`), NOT `KindRole`: an instant-replay clip is an .mp4 that trims/plays/copies exactly like a recording, so it keeps kind `"video"` and separates only as a category. That needs `Entry::origin` (persisted `"origin": "replay"`), threaded from `GifRecorder::finished(path, fromInstantReplay)` - the export path is an .mp4 like any other, so nothing downstream can recover it. Entries written before 0.7.1 have no origin and fall back to the `Unisic_Replay_<stamp>.mp4` name every export gets. The page addresses entries by `EntryIdRole`, never by row (a proxy row means a different entry after a filter switch, and a batch delete shifts the rows behind it): `entryById`/`removeByIds`/`setFavoriteByIds`, plus `entryIds`/`entryIdsBetween`/`timestampAt` on the proxy for select-all, shift-range and the sticky date header (rows outside the viewport have no delegate, so QML cannot collect these itself).
- `src/notify/LayerShellNotifier` (layer-shell card) + `src/notify/NotificationHelper` (GNOME) - one `NotificationPopup.qml` and one `NotifCard.h` (style→size table, the settings the card reads, `effectiveSettings()` for the settings preview's unsaved overrides), two hosts. `notificationActionOrder` is a CSV of stable action ids; both hosts receive it in the same settings snapshot and QML normalizes it by dropping unknown/duplicate ids and appending newly introduced actions. Layer-shell → a card-sized overlay surface anchored to the corner. GNOME/mutter → the SAME QML on an XWayland **override-redirect** window in a second process (`--notification-helper`; one process can't host two QPA platforms), Steam-toast style. `capCustomNotification()` = layer-shell ∨ `capNotificationHelper()`, and the helper is REFUSED while `org.kde.KWin` is on the bus, so on Plasma the card exists only in a build that found `layer-shell-qt` at configure time - a build without it reports `custom=n` on the most capable desktop there is. `customNotificationReason()` names which of the four causes it is (no layer-shell in the build, X11 with no display, COSMIC, compositor without wlr-layer-shell) and both the diagnostics report and the F8 line carry it, so nobody has to diff `ldd` output against `CMakeCache.txt` again. `AppContext::m_activePopupNotif` enforces one stylized card at a time; a newer capture dismisses the previous card through whichever host owns it, allowing an old helper process to exit normally. **The alternatives are dead ends, do not retry them**: a plain Wayland toplevel cannot place itself (no positioning protocol), and the fullscreen-surface-with-input-mask trick that works for the capture overlay renders **BLACK** on mutter - it unredirects fullscreen surfaces, so their transparency is never composited. Mutter can strand XWayland hover on "inside": once the pointer reaches a native Wayland surface, XWayland freezes its pointer position and even `XQueryPointer` keeps naming the card. Silence timeouts, pointer polling, and `org.gnome.Mutter.IdleMonitor` cross-checks are unreliable. Instead the helper keeps the existing 16 px transparent shadow gutter inside its X input shape, so crossing the visible card edge clears QML hover while the pointer still belongs to XWayland. Do not shrink the helper's input mask back to the exact card rect.
- `src/diag/` - the runtime log a user can paste into an issue, in three pieces. `DiagLog` installs a `qInstallMessageHandler` that **CHAINS** to the previous one (journald behaviour unchanged) and keeps the last 500 lines in a mutex-guarded ring. **Two-phase install, and the order is load-bearing**: `DiagLog::install()` is the FIRST statement of `main()` (before `QApplication`, before the helper dispatch, so QPA/QML-engine warnings are caught and a crash during construction still reports), but the FILE is opened only after this process has WON the single-instance handshake - every `return` above that point belongs to a process that forwarded its command to the running instance, and rotating the log from one of those would throw away the running instance's own file. Rotation is startup-only (`unisic.log` -> `unisic.log.1`, 0600 in `<AppDataLocation>/logs`), so exactly the two runs that matter for a crash report survive; `aboutToQuit` writes `=== clean exit ===`, and its ABSENCE is what lets the next start tell a crash from a SIGKILL/OOM. `CrashHandler` is a separate TU whose stated rule is **async-signal-safe calls only** - `write`/`open`/`raise`/`sigaction`/`backtrace`/`backtrace_symbols_fd` and nothing else (NOT `backtrace_symbols`, NOT `snprintf`, NOT `QString`); 64 KiB `sigaltstack` + `SA_ONSTACK` so a stack-overflow SEGV can still print, `backtrace()` warmed once at install so the unwinder's lazy `dlopen` is not attempted from a handler, `alarm(5)` so a wedged handler still dies, and it re-raises with `SIG_DFL` so systemd-coredump still gets a core. Compiled out under ASan/TSan. **Privacy is one choke point**: `DiagRedact::redact()` runs on EVERY line before it is stored, masking header/JSON/assignment-shaped secrets, URL userinfo and query strings, and shortening `$HOME` - because `destinations.json` holds live upload tokens and the user pastes this into a public tracker. `tests/DiagRedactTest.cpp` pins that contract. The two subprocess helpers keep NO file: they tag their lines to fd 2 and `AppContext` folds each helper's **stderr only** (stdout is their action protocol) into the one merged log.
- `src/theme/ThemeController` - module QML singleton (`QML_SINGLETON`) owning the selected theme (persisted `ui/theme`) and bridging the live system palette (`qApp->palette()` + `QStyleHints::colorScheme()`) for the "system" theme. `ThemeController::instance()` shares the one engine-created object with `IconImageProvider`. **Do NOT `qmlRegisterSingletonInstance` into the `Unisic` URI** - that clobbers the module's other C++ QML_ELEMENT types (e.g. `AnnotationCanvas` becomes "not a type"). **Community themes**: `<config dir>/themes/*.json` (schema = Theme.qml's `_defs` seed: 8 required colors + `isDark`, every `_expand()` token an optional override; parser `src/theme/ThemeJson.h`, header-only, unit-tested). **Built-in split**: core `system`/`unisic`/`dark`/`light` are hardcoded in Theme.qml's `_defs` (`unisic` is the mandatory palette AND the fallback for every unresolvable id - do not remove); the decorative palettes (Catppuccin ×2, Dracula, Nord, Gruvbox) are shipped as REAL editable JSON files: `resources/themes/*.json` lives in qrc only as the SEED SOURCE, and `ThemeController::seedThemesFolder()` copies them into `<config>/themes/` ONCE PER FILE, recorded by name in `ui/themesSeededFiles` (deleting a seeded file keeps it gone, never re-created; existing files never clobbered; a theme SHIPPED LATER is not in the record, so it still reaches an existing install). **A missing themes folder resets that record**, because the settings key travels where the files do not: a config restored from a backup or a dotfiles repo, and the dev build's config, which `Settings`' constructor seeds key-by-key from the stable one (`src/Settings.h`), both arrive claiming "already seeded" with no folder - verified as the state of this repo owner's own two configs, where the decorative themes had silently stopped existing and the F8 step reported `custom themes: FAIL`. The old single `ui/themesSeeded` bool is still written for a downgrade, and still honoured as "everything shipped at that time was delivered" when the folder DOES exist. `tests/ThemeSeedTest.cpp` pins all five cases (fresh, restored-without-folder, deleted-stays-deleted, legacy-flag backfill, newly-shipped theme); the F8 step tells "never delivered here" (FAIL) from "user deleted it" (PASS, counted) through `ThemeController::seededThemes()`. They then load through the normal custom-theme scan as `custom:<stem>` ids. `ThemeJsonTest::shippedThemesAllParse` parses every shipped JSON from the source tree so a broken seed fails tests, never a user. Resolution order in Theme.qml `pal`: core → `custom:` (incl. seeded decoratives) → unisic fallback. ThemeController scans + hot-reloads via QFileSystemWatcher (dir AND files re-armed each scan - the watcher drops deleted paths), exposes `customThemes`/`customDefs`/`customThemeErrors`, ids are `"custom:<file-stem>"`; Theme.qml resolves them in `pal` with a stock-palette fallback when the file is gone (selection kept). Editing the ACTIVE custom theme bumps `rev` so provider icons recolor. Recording overlays are theme tokens too (`recBadge{Bg,Text}`/`recDot`/`recordFrameContrast`/`countdown{Bg,Number}`/`keystroke{Bg,Text}`, deliberately NOT palette-derived - they sit over recorded content): RecordBorder.qml reads them directly; the keystroke painter gets them via `GifRecorder::setKeystrokeThemeProvider` (lazy - the recorder outlives engine construction order); the GNOME helper gets them as 6 trailing HexArgb argv colors (alpha matters for pill/disc/frame).
