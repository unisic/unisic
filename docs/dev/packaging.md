# Packaging and distribution

Read before touching the installer (`unisic-website`: `public/install.sh`), `packaging/`, release workflows, or `UpdateChecker`.

**End-user install: `install.sh`, which since 0.8.8 lives in the `unisic-website` repo as `public/install.sh`** (NOT in this repo and NOT part of the build; run `bash <(curl -fsSL https://unisic.app/install.sh)`, or `curl … | bash` - the menu reads `/dev/tty`, so a pipe still works. The site serves it as `text/plain` with `Cache-Control: no-cache` (its `nginx.conf`), so a browser shows it and nobody runs a stale copy. Edit it there; this repo keeps no copy, so there is nothing to re-sync). A single self-contained bash script that is **TUI-only, no CLI** (deliberately - see the iteration history): running it opens a **btop-style bordered arrow-key menu** in the terminal's **alternate-screen buffer**, so the whole run (menu *and* install output) lives in its own "window" and the terminal is restored to the command line on exit, leaving only a thank-you. It is ONE morphing menu: the main screen offers **Install or update / Settings / Remove / Quit** under a green install-status line (`installed_status()`: what's installed + auto-update state, or "not installed yet"), and each of the first three opens its own submenu - Install (the recommended entry, id `auto`, the passwordless portable one / `native`, the system package / "install a specific version" → version picker), Settings (auto-updates timer toggle + pre-release toggle, both flip in place), Remove (uninstall ± delete settings). Full-redrawn in place each key, never a second screen; `q`/Esc backs out one level (submenu → main, version picker → Install). The only non-interactive entry is the private `--self-update <appimage|tarball|native> <prefix> [pre]`; the auto-update timer runs the portable channels, and Unisic's in-app "Install now" (native `/usr` package installs only - see `UpdateChecker::installViaScript`) runs the `native` channel inside a terminal it spawns so the `sudo` prompt has somewhere to go. **That copy stands on TLS and a marker check, nothing more**: `installerScriptUrl()` fetches `https://unisic.app/install.sh`, the one copy there is (from 0.8.8 on no release carries the script as an asset, so GitHub publishes no digest for it), and `fetchInstallerScript()` refuses bytes without the `Unisic universal installer` marker. The script body is one `{ ... }` group closed on its last line, so a truncated download fails to parse instead of running half of it. Unisic 0.8.7 and older fall back to the per-tag `scripts/install.sh`, which does not exist from 0.8.8 on, so their "Install now" fails and those installs update by running the one-line install again. **Every OTHER downloaded file is checked against the digest GitHub publishes for it, and there are two of them**: (1) `verify_digest()` runs inside `download()` in `install.sh`, so every release asset it fetches (`.deb`/`.rpm`/`.pkg.tar.zst`/`.flatpak`/AppImage/tarball) is matched against the digest carried in the same `$RELEASE_JSON` the URL came from - one `grep -oE '"digest".*"browser_download_url"'` pair per asset, no jq and no second request, and a mismatch deletes the file and `die`s instead of handing it to a package manager; a URL with no digest in the feed (an old release, the `RAW_URL` site copy) is skipped silently, a system with no `sha256sum` with a warning. (2) `UpdateChecker::downloadAndInstall()` hashes the AppImage **as it streams** (`QCryptographicHash` fed from `readyRead`, never a second 100 MB read) and refuses to `rename()` it over the running app unless it matches `m_assetSha256` - the size check alone said nothing about the bytes, and this path installs with no further confirmation. `setup_autoupdate()`'s copy of the script for the systemd timer is `$0` when it is on disk, and `RAW_URL` with the marker check on top when piped through `curl | bash`. There are no user-facing flags. It auto-detects the distro from `/etc/os-release` and, on every native route, **installs from Unisic's own repository first** (`add_apt_repo`/`add_copr_repo`/`install_zypper_repo`), falling back to the GitHub release asset only where there is no build for that distro release, or when a specific older version was picked in the version picker (a repo only ever offers the newest). **This is not a preference, it is the only route that works**: a native package is welded to the exact Qt it was built against - the `.deb` records `qt6-base-private-abi (= <ver>)` because *any* Qt6 QML app references the private `QQmlPrivate::AOTCompiledContext` symbols that `qt_add_qml_module` generates (verified: 37 undefined `QQmlPrivate::` symbols in the built binary, none from a private header in `src/`), and the Fedora rpm links Qt private symbols too. The release `.deb` is built in `debian:trixie`, so it pins `= 6.8.2` and **cannot** install on Ubuntu 26.04 (Qt 6.10.2) - issue #93, where `install.sh` downloaded it anyway and dead-ended the user on the AppImage. `obs_deb_target()` mirrors `packaging/deb/postinst` (Debian 13, xUbuntu 25.10/26.04) and **must be updated together with it**; the key comes from `${OBS_BASE}/<target>/Release.key` into `/etc/apt/keyrings/unisic.asc` (the package's own `/usr/share/unisic/obs-signing-key.asc` does not exist before the first install), `add_copr_repo` writes `/etc/yum.repos.d/unisic-copr.repo` byte-for-byte identical to `packaging/rpm/copr-post.sh`, and `do_uninstall` removes both, since a repo-built package carries no scriptlet to drop them. An apt distro with no target gets a warning, one attempt at the Debian 13 `.deb`, and the portable tarball when that is refused, rather than `native_fail`'s dead end. `repo_lag_note()` says so plainly when the repo build is behind the release page (as `xUbuntu_25.10` is: 0.7.5 vs 0.8.1). Arch keeps `pacman -U` of the asset on purpose: `pacman -Sy <pkg>` is the partial-upgrade footgun, and the asset's `unisic.install` registers the OBS pacman repo anyway (the AUR path deliberately does not - see `packaging/aur/`). Fallback assets: `.fedora.x86_64.rpm` (**Fedora only**), `.pkg.tar.zst` (Arch). **`auto` on a machine with nothing installed resolves to `appimage`, not to the native package** (since 0.8.5): it needs no password, and from then on the app updates itself in place instead of waiting for this script to be run again - the native route is still one keypress away in the menu, and is what the in-app "Install now" forces. The chain is: an installed native package → `native`, else an installed Flatpak → `flatpak`, else an unpacked portable copy in `${PREFIX}/lib/unisic-*-x86_64` → `tarball`, else `appimage`. The first three exist so a second copy is never installed beside an existing one; the tarball branch is also where `appimage` lands when `--appimage-version` fails on the freshly downloaded file (no `/dev/fuse` or no `fusermount`: containers, hardened kernels), since the tarball is that same build already unpacked. `install_appimage_desktop()` then writes `~/.local/share/applications/app.unisic.Unisic.desktop` (+ the scalable icon), both `--appimage-extract`ed **from the AppImage that was just installed** so they always match it, with `Exec=` rewritten to the absolute `${PREFIX}/bin/unisic`. It buys the applications-menu entry and a stable app id for the portal permission store, NOT the KWin `ScreenShot2` fast path: an AppImage's `/proc/<pid>/exe` is the transient FUSE mount, so that authorization cannot match any installed path (the same reason `main.cpp::ensureDesktopFile()` skips AppImage runs). `uninstall_portable()` removes both, but only together with the copy they point at. `prune_portable()` (called by BOTH portable installers, including their "already newest" early return) deletes every other `lib/unisic/*.AppImage` and `lib/unisic-*-x86_64` afterwards: the version is in the name, so each update used to land beside its predecessor and leave ~62 MB (AppImage) or ~185 MB (unpacked tarball) behind per release, forever. It runs only once the new copy is installed and `bin/unisic` points at it, so a failed install never eats the working version, and unlinking the file a running AppImage is mounted from is safe (the inode outlives the last descriptor). The in-app self-update never grew anything: `downloadAndInstall()` renames `<asset>.part` over `$APPIMAGE` itself, and the package-install staging dirs are pruned by `pruneStages`/`cleanStaleStage`. One consequence worth knowing: after an in-app self-update the file keeps the OLD version's name (it was renamed in place), so a later `install.sh` run sees no `Unisic-<new>-x86_64.AppImage`, downloads it once more, and prunes the misnamed one - one wasted download, still exactly one copy left on disk. A **flatpak channel** sits beside those (`install_flatpak`, offered in the Install submenu only where the `flatpak` command exists, and `--self-update flatpak`): a sandboxed app can never update itself (that needs `--talk-name=org.freedesktop.Flatpak`, which Flathub rejects), so this host-side script is the updater. `flathub_has_app()` probes the Flathub API - while the listing is missing it installs the `.flatpak` release asset as a bundle (`--reinstall` over an existing one, since a bundle carries no remote to update from), and the moment the listing exists it moves that install onto the flathub remote and plain `flatpak update` takes over. `flatpak_scope()` picks `--user` vs `--system` (system goes through `priv`; the auto-update timer refuses a system install, whose password prompt has nowhere to go). `auto` never PICKS flatpak, but it does update an existing Flatpak install rather than installing a second copy beside it - unless a native package is installed, which wins. Either route leaves the OBS/COPR update repo registered (the installer adds it before installing; the CI packages' own scriptlets add it after), so re-running also updates; the menu also uninstalls (± delete settings), installs **older versions** (version picker), and toggles a **systemd-user daily auto-update timer** (portable channels) + pre-releases. On an **X11** session it CONFIRMS after install that screenshots, annotation, uploading, screen recording (video and GIF) and global hotkeys all work there, because `HAVE_X11`/`HAVE_X11_HOTKEYS` are hard build requirements carried by every recipe and no package can arrive without them; only recording a single WINDOW stays Wayland-only, since the picker is the portal's. If release-asset naming, the update repos, or supported channels change, update this script too. Details live in `AGENTS.md` §3.
**Flatpak / Flathub: `packaging/flatpak/`** (manifest + `build.sh` + a README that is the submission checklist). The KDE runtime covers Qt 6, KF6, PipeWire and its `pw-record`/`pw-dump`/`pw-play` tools; the manifest additionally builds **x264 + ffmpeg** (the runtime's ffmpeg has NO software H.264 encoder, so MP4 recording would need a VAAPI GPU and the GIF pipeline's `libx264rgb` intermediate would fail outright; `org.freedesktop.Platform.ffmpeg-full` is not usable, it stops at branch 24.08 while KDE 6.11 is 25.08), leptonica + tesseract + `eng`/`pol`/`osd` traineddata (the sandbox cannot read host langpacks), zxing-cpp, grim, wl-clipboard, an SFTP-capable curl and layer-shell-qt. **Six code paths branch on `FLATPAK_ID`**, each because the sandbox makes the normal route impossible, not as a preference: `KWinScreenShot2::isAvailable` returns false (KWin authorizes its restricted interface by the caller's exe path against the installed .desktop, which a sandboxed client can never match); `registerHostAppId` and `PortalGlobalShortcuts::registerAppId` skip the self-assignment (identity comes from the sandbox metadata); `PortalScreenshot::candidateAppIds` grants the silent-screenshot permission to the flatpak id ALONE (never the anonymous `""` host bucket); `execStagedUpdate` never stages; `UpdateChecker::installKind()` is `"flatpak"` and `updatesManagedExternally()` turns the whole Updates pane into an explanation - no GitHub request at all, because the only possible outcome would be "go run flatpak update" (which `install.sh` does for the user, from outside the sandbox); and autostart goes through `org.freedesktop.portal.Background.RequestBackground` (`autostart: true` + `commandline`), because `$XDG_CONFIG_HOME/autostart` inside the sandbox is `~/.var/app/<id>/config`, which the host session never reads. The portal has no getter, so the ANSWER it gave is persisted as `ui/portalAutostartGranted` - a refusal leaves the switch off, which is the honest reading.
**AUR: `packaging/aur/`** (`unisic` source build + `unisic-bin` release repack + `sync.sh` + a README that is the publish checklist). Deliberately NOT `packaging/arch/PKGBUILD`, which feeds OBS and the release asset and whose `unisic.install` appends the OBS pacman repo to `/etc/pacman.conf`: an AUR package may never enable a third-party repo, and here it would also fight the helper. **pacman cannot use the AUR as a repository** - the AUR hosts recipes, not built packages, so there is no sync DB for `pacman -Syu`. Only a helper (`paru`/`yay`/`pikaur`/`trizen`/`aura`/…, never yay alone) updates an AUR package, by matching *foreign* packages (`pacman -Qm`) against the AUR **by name** - which is also how a directly downloaded `.pkg.tar.zst` named `unisic` gets adopted, and why a successfully registered OBS repo instead keeps it non-foreign. Exactly one channel ever owns an install. Both recipes install `/usr/share/unisic/install-channel` containing `aur`; `UpdateChecker::installKind()` reads it (value WHITELISTED so a stray file cannot invent a kind, cached, resolved from `applicationDirPath()/../share` so a non-`/usr` prefix works) and `updatesManagedExternally()` then covers flatpak ∨ aur, which kills the GitHub check and both install buttons - "Install now" runs `install.sh --self-update native`, which `pacman -U`s the GitHub package OVER the helper's AND appends the OBS repo. `install.sh` carries the same guard (`aur_owned()` - the marker or an installed `unisic-bin`, NOT `pacman -Qm`, which a failed-repo direct install also matches - plus `aur_helper()`), and prefers a helper for fresh Arch installs; because "Install now" fetches `install.sh` fresh from the newest release (or unisic.app) every time, that guard protects releases built before the marker existed. **Source tarballs**: GitHub's tag archives NEVER contain submodules, so from the `external/unisic-kit` split onward the `unisic` recipe needs a second kit tarball pinned by commit (or a complete source tarball published as a release asset) - see the README. `sync.sh` retargets both recipes at a release, refuses to publish when the released package needs a dependency the recipes lack (extras are fine - `libinput`/`hicolor-icon-theme` are namcap findings upstream still under-declares), and regenerates `.SRCINFO` with `makepkg --printsrcinfo` in a container, because the AUR web interface reads `.SRCINFO` and not the PKGBUILD. `.github/workflows/aur.yml` (called by `release.yml`, and `workflow_dispatch`-able on its own because a re-run of the pipeline skips everything once the tag exists) runs all of that after each release (unprivileged `builder` + passwordless sudo, since makepkg refuses root and `-s` needs sudo; `AUR_SSH_KEY` secret; `aur.archlinux.org`'s host key PINNED, never `ssh-keyscan`), with `--check bin` only - the `arch` job already compiled this tree, so building the source recipe again verifies nothing - and it SKIPS pre-releases, because an AUR name with no channel in it means stable.
**Windows portable zip: `packaging/windows/deploy.sh` + `.github/workflows/windows.yml`** (since 0.8.8). `deploy.sh <build-dir> <out-dir> [<zip-dir>]` stages the windeployqt bundle and packs `bin/` and `share/` into `Unisic-<version>-windows-x86_64-experimental.zip` with `System32\tar.exe`, the same bsdtar the app unpacks with. Neither Windows file gets a `.sha256`: GitHub publishes each asset's digest, the app checks the zip against it and the release page shows it by every file. `release.yml` runs it as the `windows` job with `build-number:` (a reusable workflow does not see the caller's `UNISIC_BUILD_NUMBER`, and a build without one is `dev`, which never updates itself), outside the release job's `needs` like the Flatpak, and `windows-asset` attaches the zip and the installer afterwards. The asset name is a contract with `UpdateChecker::isInstallAsset()` in `src/update/StagedUpdate_win.cpp` (`^Unisic-.*-windows-x86_64(-experimental)?\.zip$`): rename one and Windows installs stop finding their update. `-experimental` is in the name because the port is a preview and the release page is where a user picks it; the regex keeps the suffix optional so the release that drops it is still found by every copy installed before then, while any other rename still strands them. How the update is staged and started is in `AGENTS.md` §3.

**Windows: `packaging/windows/`** (the preview port; the zip above and the installer are its release assets, the folder is a CI artifact). `deploy.sh` stages the self-contained folder (`bin/` + `share/tessdata/` + `LICENSE`) that ships as the `windows-portable` artifact, and `unisic.iss` wraps that same folder in an Inno Setup 6 wizard, the `windows-installer` artifact `unisic-<version>-windows-x64-experimental-setup.exe` (the CI job and `windows-asset` find it as `*-setup.exe`, so keep that ending). A numbered build also copies it into `release-win`, after the install/uninstall check below, so `windows-asset` attaches it beside the zip; the app never downloads it. It installs **per user, without admin rights** (`PrivilegesRequired=lowest`), into `%LOCALAPPDATA%\Programs\Unisic`, with a Start menu shortcut (the desktop icon is opt-in) and an uninstall entry at `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\{E5B31D14-31A5-4639-800D-2E19950EFEC3}_is1`. Per user on purpose: no admin prompt, and nothing outside the profile is touched. **Never change the `AppId`**: it is how an upgrade finds the copy it replaces, and a new one installs a second Unisic next to the first. An upgrade deletes `{app}\bin` and `{app}\share` before it copies (`[InstallDelete]`), so a Qt plugin or QML module a newer version dropped is not left for Qt to load, and `CloseApplications=yes` closes a running Unisic (it lives in the tray) through the Restart Manager instead of failing on files in use; nothing restarts it. That holds while a staged update runs: a silent upgrade over the installed launcher and the staged copy it waits on closed both and exited 0, so `CloseApplications=force` is not needed. The installed copy updates itself exactly as the zip does (`src/update/StagedUpdate_win.cpp`): a newer release is staged under `%APPDATA%\Unisic\unisic\updates` and the installed `unisic.exe` starts it, so `{app}` is only ever written by the installer. The uninstaller deletes that `updates` folder (`[UninstallDelete]`, a few hundred MB per staged version) and leaves the settings and capture history beside it. It also deletes the "Start at login" value Unisic writes itself (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `app.unisic.Unisic`, `src/platform/DesktopShell_win.cpp`) and the one Task Manager files under `Explorer\StartupApproved\Run`, through `[Registry]` lines with `ValueType: none` + `uninsdeletevalue`, so install writes nothing and an upgrade keeps the user's choice; left behind, Windows would try to start a deleted exe at every login. The dev build's value is `app.unisic.UnisicDev`, which the installer never touches. Every wizard string is one of Inno Setup's own translated messages (`{cm:...}` plus the bundled `.isl` file for each of the seven shipped languages), so the installer adds nothing to `i18n/`; a custom message would need all seven translations inside the `.iss`. Build it after `deploy.sh`, from pwsh or cmd and not from an MSYS2 shell, which rewrites `/D...` switches as paths: `iscc /DAppVersion=<UNISIC_VERSION_STRING> /DBundleDir=<abs dist-win> /DOutputDir=<abs dir> packaging\windows\unisic.iss`. The CI job installs it silently, takes one screenshot from the installed copy with only the system dirs on `PATH`, uninstalls it, and fails if the folder, a stand-in staged update, a seeded Run value, the Start menu shortcut or the uninstall key is left behind. The exe's icon comes from `src/platform/win/unisic.rc`, whose `unisic.ico` is generated from `resources/icons/unisic.svg` by `make-icon.py` (run it in a UCRT64 shell after the SVG changes; the build only reads the committed `.ico`).
**There are no optional dependencies. Every `HAVE_*` gate in `CMakeLists.txt` and `external/unisic-kit/CMakeLists.txt` is a hard requirement, and these recipes are what keep that true.** A missing `-devel` package on the builder now stops the configure with the package name in the error (`unisic_require_failed()` / `unisic_kit_require_failed()`, one line per distro), and a successful configure writes `<build>/unisic-features.txt` listing all ten distinct feature names as `NAME=ON` - so a job that produced a package produced a complete one, and a CI step can assert that instead of trusting it.

The reason the policy is this blunt is the history, which is the argument and should not be edited out. Gates used to fail SILENTLY: the build succeeded and shipped a binary whose feature was simply absent, and the only place it surfaced was a greyed row in Settings on the user's machine, months later, in a bug report. No recipe installed the libinput development files, so `HAVE_LIBINPUT` was OFF in every published package from the moment the keystroke badge and the click ripple shipped, and the rows said "no libinput support" to users who had libinput installed (`ldd /usr/bin/unisic | grep libinput` on an installed release is still the one-command check). `HAVE_KGUIADDONS` went the same way in the released rpm, `HAVE_X11` in the Nix build, and every one of those jobs was green. On Flatpak that class of mistake is permanent rather than embarrassing: whatever the manifest does not build, the sandbox can never borrow from the host, so the user cannot repair it either.

The full list a recipe must carry: runtime helpers `ffmpeg`, `curl`, `grim`, `zip`, `wl-clipboard`, the PipeWire tools and one desktop-specific portal backend, plus build/runtime libraries `pipewire`, `tesseract`+`leptonica` **plus the `eng`/`pol`/`osd` traineddata as a runtime dependency** (an engine with no language data OCRs nothing), `zxing-cpp`, `layer-shell-qt`+`wayland`, `KF6GuiAddons`, `Qt6LinguistTools` (Fedora `qt6-qttools-devel`, Debian `qt6-tools-dev`+`qt6-l10n-tools`, Arch `qt6-tools`; without it the build ships English only while the picker still offers seven languages), `Qt6WaylandClient` + the **Qt6 GUI private headers** + `plasma-wayland-protocols` (+`wayland-scanner`) for KWin-native recording, `x11`+`xext`+`xfixes`+`xcb`, and **`libinput` + `libudev` together** - CMake needs BOTH pkg-config modules for the one define, and on Fedora `libudev.pc` lives in `systemd-devel`, not in anything named libudev (Debian: `libinput-dev` + `libudev-dev`; Arch: `libinput`, whose `systemd-libs` dependency carries `libudev.pc`). The PipeWire CLI split differs by distro: Debian `pipewire-bin`, Fedora `pipewire-utils`, Arch `pipewire` (`pw-dump`) + `pipewire-audio` (`pw-record`/`pw-play`), openSUSE `pipewire-tools`. Portal backends are hard without choosing a foreign desktop: Debian `xdg-desktop-portal-backend`, Arch `xdg-desktop-portal-impl`, RPM rich alternatives. The places to change together: `.github/workflows/{rpm,deb,appimage,arch,nix}.yml`, `unisic.spec` (COPR/Packit and the openSUSE side of OBS), `packaging/obs/{unisic.dsc,debian.control}`, `packaging/arch/PKGBUILD` (both `depends` and `makedepends`), `packaging/aur/unisic{,-bin}/PKGBUILD` + `.SRCINFO`, `nix/package.nix`, and the Flatpak manifest.

Two channels needed real work to make the rule hold, and neither is an exception to it. **Flatpak carries libinput itself**: the KDE runtime has `libudev.so.1` but no libinput at all (verified against `org.freedesktop.Platform` 25.08), so the manifest builds libevdev + mtdev + libinput as pinned modules, and `finish-args` gains `--device=input` plus `--filesystem=/run/udev:ro` - the library alone links but reads nothing, because the sandbox has to be allowed at `/dev/input` as well. The pressed-key badge and the click ripple therefore work in the Flatpak like everywhere else, and `InputPermission` can only ever report on the user's own device access. **Debian 13 needed a kit-side fallback for the Qt6 GUI private headers**: trixie's `qt6-base-private-dev` installs the headers but ships no `Qt6GuiPrivateConfig.cmake` at all (sid moved the config into `qt6-base-dev`), so `find_package(Qt6 COMPONENTS GuiPrivate)` fails on a system that has everything the code needs. The kit falls back to `find_path()` for `qpa/qplatformnativeinterface.h` under `Qt6Gui_INCLUDE_DIRS/<version>/QtGui` and prints which of the two routes it took, because a fallback nobody can see is how this class of bug survives in the first place. Keep the header package in the deb list even though the config-file probe is what normally succeeds.

When a `HAVE_*` gate is added, add its `unisic_require_failed()` branch AND its packages to every file in that list in the SAME commit - a feature that exists only in the maintainer's own build is worse than no feature, because the UI promises it.
