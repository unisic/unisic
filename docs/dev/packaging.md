# Packaging and distribution

Read before touching `scripts/install.sh`, `packaging/`, release workflows, or `UpdateChecker`.

**End-user install: `scripts/install.sh`** (NOT part of the build; run `bash <(curl -fsSL https://raw.githubusercontent.com/unisic/unisic/main/scripts/install.sh)`, or `curl … | bash` - the menu reads `/dev/tty`, so a pipe still works). A single self-contained bash script that is **TUI-only, no CLI** (deliberately - see the iteration history): running it opens a **btop-style bordered arrow-key menu** in the terminal's **alternate-screen buffer**, so the whole run (menu *and* install output) lives in its own "window" and the terminal is restored to the command line on exit, leaving only a thank-you. It is ONE morphing menu: the main screen offers **Install or update / Settings / Remove / Quit** under a green install-status line (`installed_status()`: what's installed + auto-update state, or "not installed yet"), and each of the first three opens its own submenu - Install (recommended install / portable / "install a specific version" → version picker), Settings (auto-updates timer toggle + pre-release toggle, both flip in place), Remove (uninstall ± delete settings). Full-redrawn in place each key, never a second screen; `q`/Esc backs out one level (submenu → main, version picker → Install). The only non-interactive entry is the private `--self-update <appimage|tarball|native> <prefix> [pre]`; the auto-update timer runs the portable channels, and Unisic's in-app "Install now" (native `/usr` package installs only - see `UpdateChecker::installViaScript`) runs the `native` channel inside a terminal it spawns so the `sudo` prompt has somewhere to go. **That copy is verified before it runs**: `release.yml` stages `scripts/install.sh` into `dist/`, so every release publishes the script as its own asset and GitHub computes a `digest` (`"sha256:<hex>"`) for it; the release-asset loop in `UpdateChecker::parseRelease` captures both, `installerScriptUrl()` then prefers that asset over `raw.githubusercontent.com/.../main/scripts/install.sh`, and `fetchInstallerScript()` refuses to hand the bytes to `installViaScript` unless their sha256 matches. The branch head is the fallback ONLY: it moves under the release it is supposed to belong to, so no hash can ever be pinned to it. Both ends are GitHub, so this is no defence against GitHub itself - it catches a truncated or resumed-wrong download, a caching proxy serving a stale copy, and tampering at one endpoint but not the other. Releases cut before the script became an asset carry no digest: the `Unisic universal installer` marker check still runs, a `qWarning` records that nothing stronger was possible, and the dev button / F8 line says which of the two paths it took (a PASS that does not say `sha256 verified` only means the file downloaded and parsed). There are no user-facing flags. It auto-detects the distro from `/etc/os-release` and, on every native route, **installs from Unisic's own repository first** (`add_apt_repo`/`add_copr_repo`/`install_zypper_repo`), falling back to the GitHub release asset only where there is no build for that distro release, or when a specific older version was picked in the version picker (a repo only ever offers the newest). **This is not a preference, it is the only route that works**: a native package is welded to the exact Qt it was built against - the `.deb` records `qt6-base-private-abi (= <ver>)` because *any* Qt6 QML app references the private `QQmlPrivate::AOTCompiledContext` symbols that `qt_add_qml_module` generates (verified: 37 undefined `QQmlPrivate::` symbols in the built binary, none from a private header in `src/`), and the Fedora rpm links Qt private symbols too. The release `.deb` is built in `debian:trixie`, so it pins `= 6.8.2` and **cannot** install on Ubuntu 26.04 (Qt 6.10.2) - issue #93, where `install.sh` downloaded it anyway and dead-ended the user on the AppImage. `obs_deb_target()` mirrors `packaging/deb/postinst` (Debian 13, xUbuntu 25.10/26.04) and **must be updated together with it**; the key comes from `${OBS_BASE}/<target>/Release.key` into `/etc/apt/keyrings/unisic.asc` (the package's own `/usr/share/unisic/obs-signing-key.asc` does not exist before the first install), `add_copr_repo` writes `/etc/yum.repos.d/unisic-copr.repo` byte-for-byte identical to `packaging/rpm/copr-post.sh`, and `do_uninstall` removes both, since a repo-built package carries no scriptlet to drop them. An apt distro with no target gets a warning, one attempt at the Debian 13 `.deb`, and the portable tarball when that is refused, rather than `native_fail`'s dead end. `repo_lag_note()` says so plainly when the repo build is behind the release page (as `xUbuntu_25.10` is: 0.7.5 vs 0.8.1). Arch keeps `pacman -U` of the asset on purpose: `pacman -Sy <pkg>` is the partial-upgrade footgun, and the asset's `unisic.install` registers the OBS pacman repo anyway (the AUR path deliberately does not - see `packaging/aur/`). Fallback assets: `.fedora.x86_64.rpm` (**Fedora only**), `.pkg.tar.zst` (Arch); **atomic/immutable desktops** (Silverblue/Kinoite/Bazzite/…, detected via `/run/ostree-booted`) and any distro with no native package get the self-updating **AppImage** / portable `.tar.gz` in `~/.local` (no password). A **flatpak channel** sits beside those (`install_flatpak`, offered in the Install submenu only where the `flatpak` command exists, and `--self-update flatpak`): a sandboxed app can never update itself (that needs `--talk-name=org.freedesktop.Flatpak`, which Flathub rejects), so this host-side script is the updater. `flathub_has_app()` probes the Flathub API - while the listing is missing it installs the `.flatpak` release asset as a bundle (`--reinstall` over an existing one, since a bundle carries no remote to update from), and the moment the listing exists it moves that install onto the flathub remote and plain `flatpak update` takes over. `flatpak_scope()` picks `--user` vs `--system` (system goes through `priv`; the auto-update timer refuses a system install, whose password prompt has nowhere to go). `auto` never PICKS flatpak, but it does update an existing Flatpak install rather than installing a second copy beside it - unless a native package is installed, which wins. Either route leaves the OBS/COPR update repo registered (the installer adds it before installing; the CI packages' own scriptlets add it after), so re-running also updates; the menu also uninstalls (± delete settings), installs **older versions** (version picker), and toggles a **systemd-user daily auto-update timer** (portable channels) + pre-releases. On an **X11** session it warns after install that screen recording won't work (screenshots/annotate/upload do; recording needs the Wayland-only ScreenCast portal - verified in `src/capture` vs `src/record`). If release-asset naming, the update repos, or supported channels change, update this script too. Details live in `AGENTS.md` §3.
**Flatpak / Flathub: `packaging/flatpak/`** (manifest + `build.sh` + a README that is the submission checklist). The KDE runtime covers Qt 6, KF6 and PipeWire; the manifest additionally builds **x264 + ffmpeg** (the runtime's ffmpeg has NO software H.264 encoder, so MP4 recording would need a VAAPI GPU and the GIF pipeline's `libx264rgb` intermediate would fail outright; `org.freedesktop.Platform.ffmpeg-full` is not usable, it stops at branch 24.08 while KDE 6.11 is 25.08), leptonica + tesseract + `eng`/`pol` traineddata (the sandbox cannot read host langpacks), zxing-cpp, wl-clipboard and layer-shell-qt. **Six code paths branch on `FLATPAK_ID`**, each because the sandbox makes the normal route impossible, not as a preference: `KWinScreenShot2::isAvailable` returns false (KWin authorizes its restricted interface by the caller's exe path against the installed .desktop, which a sandboxed client can never match); `registerHostAppId` and `PortalGlobalShortcuts::registerAppId` skip the self-assignment (identity comes from the sandbox metadata); `PortalScreenshot::candidateAppIds` grants the silent-screenshot permission to the flatpak id ALONE (never the anonymous `""` host bucket); `execStagedUpdate` never stages; `UpdateChecker::installKind()` is `"flatpak"` and `updatesManagedExternally()` turns the whole Updates pane into an explanation - no GitHub request at all, because the only possible outcome would be "go run flatpak update" (which `scripts/install.sh` does for the user, from outside the sandbox); and autostart goes through `org.freedesktop.portal.Background.RequestBackground` (`autostart: true` + `commandline`), because `$XDG_CONFIG_HOME/autostart` inside the sandbox is `~/.var/app/<id>/config`, which the host session never reads. The portal has no getter, so the ANSWER it gave is persisted as `ui/portalAutostartGranted` - a refusal leaves the switch off, which is the honest reading.
**AUR: `packaging/aur/`** (`unisic` source build + `unisic-bin` release repack + `sync.sh` + a README that is the publish checklist). Deliberately NOT `packaging/arch/PKGBUILD`, which feeds OBS and the release asset and whose `unisic.install` appends the OBS pacman repo to `/etc/pacman.conf`: an AUR package may never enable a third-party repo, and here it would also fight the helper. **pacman cannot use the AUR as a repository** - the AUR hosts recipes, not built packages, so there is no sync DB for `pacman -Syu`. Only a helper (`paru`/`yay`/`pikaur`/`trizen`/`aura`/…, never yay alone) updates an AUR package, by matching *foreign* packages (`pacman -Qm`) against the AUR **by name** - which is also how a directly downloaded `.pkg.tar.zst` named `unisic` gets adopted, and why a successfully registered OBS repo instead keeps it non-foreign. Exactly one channel ever owns an install. Both recipes install `/usr/share/unisic/install-channel` containing `aur`; `UpdateChecker::installKind()` reads it (value WHITELISTED so a stray file cannot invent a kind, cached, resolved from `applicationDirPath()/../share` so a non-`/usr` prefix works) and `updatesManagedExternally()` then covers flatpak ∨ aur, which kills the GitHub check and both install buttons - "Install now" runs `install.sh --self-update native`, which `pacman -U`s the GitHub package OVER the helper's AND appends the OBS repo. `install.sh` carries the same guard (`aur_owned()` - the marker or an installed `unisic-bin`, NOT `pacman -Qm`, which a failed-repo direct install also matches - plus `aur_helper()`), and prefers a helper for fresh Arch installs; because "Install now" fetches `install.sh` fresh from the repo every time, that guard protects releases built before the marker existed. **Source tarballs**: GitHub's tag archives NEVER contain submodules, so from the `external/unisic-kit` split onward the `unisic` recipe needs a second kit tarball pinned by commit (or a complete source tarball published as a release asset) - see the README. `sync.sh` retargets both recipes at a release, refuses to publish when the released package needs a dependency the recipes lack (extras are fine - `libinput`/`hicolor-icon-theme` are namcap findings upstream still under-declares), and regenerates `.SRCINFO` with `makepkg --printsrcinfo` in a container, because the AUR web interface reads `.SRCINFO` and not the PKGBUILD. `.github/workflows/aur.yml` (called by `release.yml`, and `workflow_dispatch`-able on its own because a re-run of the pipeline skips everything once the tag exists) runs all of that after each release (unprivileged `builder` + passwordless sudo, since makepkg refuses root and `-s` needs sudo; `AUR_SSH_KEY` secret; `aur.archlinux.org`'s host key PINNED, never `ssh-keyscan`), with `--check bin` only - the `arch` job already compiled this tree, so building the source recipe again verifies nothing - and it SKIPS pre-releases, because an AUR name with no channel in it means stable.
