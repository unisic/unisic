# Packaging and distribution

Read before touching `scripts/install.sh`, `packaging/`, release workflows, or `UpdateChecker`.

**End-user install: `scripts/install.sh`** (NOT part of the build; run `bash <(curl -fsSL https://raw.githubusercontent.com/unisic/unisic/main/scripts/install.sh)`, or `curl … | bash` - the menu reads `/dev/tty`, so a pipe still works). A single self-contained bash script that is **TUI-only, no CLI** (deliberately - see the iteration history): running it opens a **btop-style bordered arrow-key menu** in the terminal's **alternate-screen buffer**, so the whole run (menu *and* install output) lives in its own "window" and the terminal is restored to the command line on exit, leaving only a thank-you. It is ONE morphing menu: the main screen offers **Install or update / Settings / Remove / Quit** under a green install-status line (`installed_status()`: what's installed + auto-update state, or "not installed yet"), and each of the first three opens its own submenu - Install (recommended install / portable / "install a specific version" → version picker), Settings (auto-updates timer toggle + pre-release toggle, both flip in place), Remove (uninstall ± delete settings). Full-redrawn in place each key, never a second screen; `q`/Esc backs out one level (submenu → main, version picker → Install). The only non-interactive entry is the private `--self-update <appimage|tarball|native> <prefix> [pre]`; the auto-update timer runs the portable channels, and Unisic's in-app "Install now" (native `/usr` package installs only - see `UpdateChecker::installViaScript`) runs the `native` channel inside a terminal it spawns so the `sudo` prompt has somewhere to go. There are no user-facing flags. It auto-detects the distro from `/etc/os-release` and installs the matching GitHub release asset: `.deb` (Debian/Ubuntu apt), `.fedora.x86_64.rpm` (**Fedora only** - the rpm links Qt PRIVATE symbols, locked to Fedora's exact Qt minor), `.pkg.tar.zst` (Arch), or adds the OBS zypper repo on openSUSE; **atomic/immutable desktops** (Silverblue/Kinoite/Bazzite/…, detected via `/run/ostree-booted`) and any distro with no native package get the self-updating **AppImage** / portable `.tar.gz` in `~/.local` (no password). A **flatpak channel** sits beside those (`install_flatpak`, offered in the Install submenu only where the `flatpak` command exists, and `--self-update flatpak`): a sandboxed app can never update itself (that needs `--talk-name=org.freedesktop.Flatpak`, which Flathub rejects), so this host-side script is the updater. `flathub_has_app()` probes the Flathub API - while the listing is missing it installs the `.flatpak` release asset as a bundle (`--reinstall` over an existing one, since a bundle carries no remote to update from), and the moment the listing exists it moves that install onto the flathub remote and plain `flatpak update` takes over. `flatpak_scope()` picks `--user` vs `--system` (system goes through `priv`; the auto-update timer refuses a system install, whose password prompt has nowhere to go). `auto` never PICKS flatpak, but it does update an existing Flatpak install rather than installing a second copy beside it - unless a native package is installed, which wins. Each native package self-registers its OBS/COPR update repo, so re-running also updates; the menu also uninstalls (± delete settings), installs **older versions** (version picker), and toggles a **systemd-user daily auto-update timer** (portable channels) + pre-releases. On an **X11** session it warns after install that screen recording won't work (screenshots/annotate/upload do; recording needs the Wayland-only ScreenCast portal - verified in `src/capture` vs `src/record`). If release-asset naming, the update repos, or supported channels change, update this script too. Details live in `AGENTS.md` §3.
**Flatpak / Flathub: `packaging/flatpak/`** (manifest + `build.sh` + a README that is the submission checklist). The KDE runtime covers Qt 6, KF6 and PipeWire; the manifest additionally builds **x264 + ffmpeg** (the runtime's ffmpeg has NO software H.264 encoder, so MP4 recording would need a VAAPI GPU and the GIF pipeline's `libx264rgb` intermediate would fail outright; `org.freedesktop.Platform.ffmpeg-full` is not usable, it stops at branch 24.08 while KDE 6.11 is 25.08), leptonica + tesseract + `eng`/`pol` traineddata (the sandbox cannot read host langpacks), zxing-cpp, wl-clipboard and layer-shell-qt. **Six code paths branch on `FLATPAK_ID`**, each because the sandbox makes the normal route impossible, not as a preference: `KWinScreenShot2::isAvailable` returns false (KWin authorizes its restricted interface by the caller's exe path against the installed .desktop, which a sandboxed client can never match); `registerHostAppId` and `PortalGlobalShortcuts::registerAppId` skip the self-assignment (identity comes from the sandbox metadata); `PortalScreenshot::candidateAppIds` grants the silent-screenshot permission to the flatpak id ALONE (never the anonymous `""` host bucket); `execStagedUpdate` never stages; `UpdateChecker::installKind()` is `"flatpak"` and `updatesManagedExternally()` turns the whole Updates pane into an explanation - no GitHub request at all, because the only possible outcome would be "go run flatpak update" (which `scripts/install.sh` does for the user, from outside the sandbox); and autostart goes through `org.freedesktop.portal.Background.RequestBackground` (`autostart: true` + `commandline`), because `$XDG_CONFIG_HOME/autostart` inside the sandbox is `~/.var/app/<id>/config`, which the host session never reads. The portal has no getter, so the ANSWER it gave is persisted as `ui/portalAutostartGranted` - a refusal leaves the switch off, which is the honest reading.
**AUR: `packaging/aur/`** (`unisic` source build + `unisic-bin` release repack + `sync.sh` + a README that is the publish checklist). Deliberately NOT `packaging/arch/PKGBUILD`, which feeds OBS and the release asset and whose `unisic.install` appends the OBS pacman repo to `/etc/pacman.conf`: an AUR package may never enable a third-party repo, and here it would also fight the helper. **pacman cannot use the AUR as a repository** - the AUR hosts recipes, not built packages, so there is no sync DB for `pacman -Syu`. Only a helper (`paru`/`yay`/`pikaur`/`trizen`/`aura`/…, never yay alone) updates an AUR package, by matching *foreign* packages (`pacman -Qm`) against the AUR **by name** - which is also how a directly downloaded `.pkg.tar.zst` named `unisic` gets adopted, and why a successfully registered OBS repo instead keeps it non-foreign. Exactly one channel ever owns an install. Both recipes install `/usr/share/unisic/install-channel` containing `aur`; `UpdateChecker::installKind()` reads it (value WHITELISTED so a stray file cannot invent a kind, cached, resolved from `applicationDirPath()/../share` so a non-`/usr` prefix works) and `updatesManagedExternally()` then covers flatpak ∨ aur, which kills the GitHub check and both install buttons - "Install now" runs `install.sh --self-update native`, which `pacman -U`s the GitHub package OVER the helper's AND appends the OBS repo. `install.sh` carries the same guard (`aur_owned()` - the marker or an installed `unisic-bin`, NOT `pacman -Qm`, which a failed-repo direct install also matches - plus `aur_helper()`), and prefers a helper for fresh Arch installs; because "Install now" fetches `install.sh` fresh from the repo every time, that guard protects releases built before the marker existed. **Source tarballs**: GitHub's tag archives NEVER contain submodules, so from the `external/unisic-kit` split onward the `unisic` recipe needs a second kit tarball pinned by commit (or a complete source tarball published as a release asset) - see the README. `sync.sh` retargets both recipes at a release, refuses to publish when the released package needs a dependency the recipes lack (extras are fine - `libinput`/`hicolor-icon-theme` are namcap findings upstream still under-declares), and regenerates `.SRCINFO` with `makepkg --printsrcinfo` in a container, because the AUR web interface reads `.SRCINFO` and not the PKGBUILD. The `aur` job in `release.yml` runs all of that after each release (unprivileged `builder` + passwordless sudo, since makepkg refuses root and `-s` needs sudo; `AUR_SSH_KEY` secret; `aur.archlinux.org`'s host key PINNED, never `ssh-keyscan`), with `--check bin` only - the `arch` job already compiled this tree, so building the source recipe again verifies nothing - and it SKIPS pre-releases, because an AUR name with no channel in it means stable.
