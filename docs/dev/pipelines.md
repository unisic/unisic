# Runtime pipelines: recording, hotkeys, clipboard, after-capture, dev mode

## Recording and global hotkeys

Recording: one `GifRecorder` parameterized by `Output{Gif,Mp4,WebM}` + `SourceType{Screen,Region,Window}`; Window source passes `types=WINDOW` to `ScreenCastSession` (portal window picker). **The active window's rectangle is an overlay feature, not a recording source**: `W` inside the region overlay selects it (`OverlayController::selectActiveWindow`, arithmetic in `docs/dev/architecture.md`), so a screenshot, an OCR read, a GIF and a recording all reach it through the one selector. A dedicated `record-window` hotkey (`Settings::hotkeyRecordWindow`, key `hotkeys/recordWindow`, `Meta+Shift+4`) existed in development and was CUT before release as too niche - do not re-add it without asking: the selector already covers it in one keypress, and every extra hotkey row is a row everyone else reads past. The rect comes from `capture/KWinWindowGeometry`: there is no D-Bus property for it, so the class loads a throwaway KWin script (`org.kde.kwin.Scripting.loadScript` → run on `/Scripting/Script<id>` → `unloadScript`) whose one line `callDBus`es `workspace.activeWindow.frameGeometry` back into us. That callback is why the object registers its own per-pid bus name (`app.unisic.kwingeom_<pid>`), exports itself with `ExportAllSlots` and pins its interface with `Q_CLASSINFO("D-Bus Interface", "app.unisic.KWinWindowGeometry")` - the name the script hardcodes. The Q_CLASSINFO is load-bearing: without it Qt derives the interface from the class **and the application name** (measured: `local.geomcheck.KWinWindowGeometry` from a probe binary, so `local.unisic.…` vs `local.unisic-dev.…` here), and KWin's call comes back `org.freedesktop.DBus.Error.UnknownInterface` while the query just times out. Teardown is DEFERRED (queued `cleanup()`), or the reply KWin is still waiting on dies with the object; a 2 s timeout covers a KWin that never answers. KWin reports GLOBAL LOGICAL px, so every consumer has to map them itself - the overlay in `selectionForScreen()` (clip to the screen, subtract its origin, scale by the frozen image), and any future physical-pixel consumer (`GifRecorder::Region` wants physical px relative to ONE screen plus that `QScreen *`) through the screen's DPR as well. `KWinWindowGeometry::isAvailable()` (KWin on the session bus) gates the whole thing, because no other compositor tells a client where another window is - and there the W hint is simply absent, not greyed: greying says "install something", while this is not a thing that exists off KWin. Covered by the `active window geometry` / `active window mapping` F8 steps and the `devTestActiveWindowGeometry` Developer button. GIF (region/screen) and video (screen/region/window → MP4/WebM) keep separate `AppContext` entry points but share ONE page: `RecordPage.qml` hosts both behind a Video/GIF segment and `GifPage.qml` is gone. Which half is showing is a persisted setting (`Settings::recordPageMode`, key `ui/recordMode`), never page state: every page lives behind a `Loader` that is destroyed on navigation, so a mode kept in the page would reset the moment you walk away from it. The Screen/Region/Window buttons keep their places across the flip and only enable/disable (GIF has no window source, and the labels deliberately do not change, because swapping them would reflow the row); what the button will produce lives in its spoken description instead. So the sidebar is five entries (Capture, Record, Edit, History, Servers) plus the Settings gear in the bottom app card, page shortcuts `Ctrl+1`…`Ctrl+6` (6 = Settings, same as `Ctrl+,`). **Video quality is stored as a percent** (`Settings::videoQualityPercent`, key `video/qualityPercent`), never as the CRF: `UnisicVideo::crfFromPercent` in `record/VideoQuality.h` derives the encoder value at every call site (recorder, replay capture, final conversion, `AppContext::trimRecording`), and the `Settings` constructor migrates a pre-0.8.3 `video/quality` CRF once, then removes the old key. The scale is linear over CRF 40..0 so `percentFromCrf`/`crfFromPercent` are exact inverses at every whole CRF, which is what makes that migration lossless; a DERIVED (non-stored) percent property would additionally fail `tests/SettingsPersistenceTest.cpp`, which writes `current + 7` into every writable int property and demands an exact fresh-process read-back. **Separate audio tracks** (`Settings::separateAudioTracks`, key `audio/separateTracks`) keeps every source as its own stream when two or more are live, but STILL leads with a full `amix` as track 1 titled `tr("Mix")`: players play only a file's first audio track, so a stems-only file sounded like "no microphone" to anyone who just watched it (user-reported as exactly that bug). The stems follow, each carrying a `title` (`tr("System audio")`/`tr("Microphone")`/`tr("Application audio")`, kept with the Mix in `m_audioTrackTitles`); a source feeding both the mix and its own stem is legal ffmpeg (verified: an input stream may enter `-filter_complex` and be `-map`ped directly in one command). The app-audio FIFO is the one input that can EOF before the recording does (pw-record dies, the node disappears); as its own stream under `-shortest` that truncates the WHOLE file to however long it lived (measured: a FIFO closing after 1 s ended a 3 s capture at 1 s), so separate-track mode routes it through `apad,asplit=2` in `-filter_complex` - one padded leg into the amix, one as the stem. `amix`'s `duration=longest` covers the mixed case, and `-shortest` cannot simply be dropped - a pulse input never EOFs, so the encode would not end at all. **Microphone input** (`Settings::microphoneSource`, key `audio/microphoneSource`) is the pulse source NAME the mic input opens (empty = `default`); stored as `node.name` (survives reboots, unlike `object.serial`), listed by `AppContext::requestAudioInputDevices()` (pw-dump nodes with `media.class` `Audio/Source`/`Audio/Source/Virtual` - monitors never appear, PipeWire models them as sink ports; same off-thread rule as the app-node query). Everything downstream must then map `0:a?`, never `0:a:0`, or a paused or trimmed recording loses the microphone silently: `pauseExciseArgs`, the single `GifRecorder::finalAudioArgs` helper (shared by the final conversion, the instant-replay export and `AppContext::trimRecording`, so the three cannot drift) and the trimmer's LOSSLESS branch all do - the lossless cut used to be a bare `-c copy` whose default stream selection silently kept ONE audio stream. The trim window additionally edits audio per track (`TrimController::loadAudioTracks` ffprobe listing; `trimRecording`'s `audioGains` arg, one value per track, -1 = drop, else volume factor): any edit routes through `GifRecorder::audioEditArgs`, which maps kept tracks explicitly and re-encodes AUDIO ONLY (`-filter:a:N` counts output streams, so it indexes kept tracks) - the video stays copied/exact in both cut modes. **The recorder's own mix track is never edited directly**: muting a stem would change nothing audible (players play track 1 = the mix, and the stem is still in it - user-reported as "audio editing does not work"). `loadAudioTracks` flags the FIRST audio track whose title is one of the recorder's own mix names (Mix/Miks/Mezcla/Микс - our strings, versioned with the app; first-track-only so a foreign file is never claimed), the window hides that row and passes `mixTrack` to `trimRecording`, and any edit then routes through `GifRecorder::audioRemixArgs`: the old mix is dropped and REBUILT by amixing the kept stems at their gains inside `-filter_complex` (which coexists with the video branch's `-vf` - verified: simple and complex graphs may share one command when they feed different output streams), stems follow as before, and the rebuilt track gets `title`+`handler_name` from the caller (`tr("Mix")`) since a filtered stream inherits no source metadata. **The preview plays the edits live too**: the kit's `VideoPreview` takes `trackGains`+`mixTrack`, mutes the main player's audio (its default track IS the mix being replaced) and voices one auxiliary audio-only `MediaPlayer` per remaining track (`Instantiator`), each pinned to its stream via `activeAudioTrack` with `AudioOutput.volume` as the gain (capped at 1.0 - the slider's 200% boost applies only to the saved file; a 90 ms `Behavior` ramp keeps toggles from clicking). With a known `mixTrack` the aux players run from the moment the window opens - stems at 1.0 sum to the mix, so the default sounds identical and an edit is ONLY a volume change, never a pipeline spawn mid-playback (each aux is a full decode pipeline; that standing cost is the price of a gapless first edit). A foreign file (`mixTrack` -1) defaults to its first track alone, so there the aux players appear only once an edit needs them. play/pause/seek fan out from the `VideoPreview` functions and the main player's ~10 Hz position ticks re-seek any aux that drifts past 200 ms - do not tighten that threshold, constant micro-seeks stutter audibly. Verified headless: `qml -platform offscreen` harness on a real 3-track recording - aux players land on tracks 1+2 with the right volumes and stay inside 300 ms of the main clock (note: the `qml` tool's console.log is suppressed by Fedora's logging config even with QT_LOGGING_RULES; assert via `Qt.exit(code)` instead). MP4 has no Matroska-style stream title, so `finalAudioArgs` writes BOTH `-metadata:s:a:N title=` (which lands as the `name` tag) and `handler_name=` - the latter is what ffprobe reads back and what an editor shows; `audioEditArgs` passes no titles and relies on ffmpeg's per-stream metadata copy. Covered by `tests/VideoQualityTest.cpp` plus the `videoQualityCheck` / `audioTracksCheck` / `trimAudioCheck` F8 steps and their Developer buttons (`devTestAudioTracks`, `devTestAudioInputs`, `devTestTrimAudio`). Recording overlays: `CursorOverlayPainter` (pointer/halo/ripples, only in CursorMetadata mode) and `KeystrokeOverlayPainter` (screenkey-style badge, `record/keystrokes`, works in EVERY cursor mode) both composite in `compositeCursorOverlay` into the reused scratch buffer - `m_lastFrame` stays clean (it is the sample-and-hold source; baking a badge in would freeze it on held frames). Key/click events come from `KeyCapture`/`ClickCapture` (libinput udev observers on their own threads, plain open no grab, `HAVE_LIBINPUT` - a hard build requirement, so the ONLY thing that can turn these off on a user's machine is `InputPermission::probe()`, which wants the `input` group and degrades silently without it). Badge labels are PHYSICAL (US) key legends: evdev codes only, the compositor's xkb layout is not observable from a libinput observer. Global hotkeys: `GlobalHotkeys::defineAction` registers with KGlobalAccel flag `IsDefault(0x8)` only (preserves KCM edits; a separate `SetPresent(0x2)` call *clears* the binding on that daemon). **The IsDefault reply lies**: when the daemon has an active binding stored as "none" it echoes the requested keys while filling only the default column - the action stays dead. So `AppContext::defineHotkeys` runs `hotkeyBindStatusAsync` on EVERY launch: real non-blocking `shortcutKeys` queries; any action reported unbound while the app stores a key gets re-asserted via `setShortcutAsync` (`SetPresent|NoAutoloading`, 0x6); a differing bound key is synced into the UI. A deliberate KCM unbind made while the app runs still sticks (the change signal empties the stored string). User edits/imports also push `setShortcut`. `GlobalHotkeys::unregisterAction` (the purge for actions we dropped - quick-copy, quick-task, capture-screen, recapture-region - and for the `alt-hotkey-test` scratch action) MUST send the FULL 4-element action id: kglobalacceld matches by list LENGTH, so a 2-element list is answered with success and does nothing (measured live: every one of those actions was still registered, and quick-task still held its Meta+Shift+Space, long after the cleanup shipped). The two friendly names are NOT compared - they go empty rather than translated, since the daemon stores whatever locale first registered the action. **Alternate hotkeys**: each action holds up to 4 bindings - stored as ONE comma-joined portable string ("Meta+Shift+S, Print"; QKeySequence chord limit), `keysFor` flattens the chords into the daemon's alternate-key list, `UShortcutList` (chips + "+ add key" recorder) edits it. The daemon REORDERS alternates in replies - every binding comparison must go through `GlobalHotkeys::sameBinding` (set-based), or reorders read as KCM edits/failures. **Non-KDE hotkeys** go through `PortalGlobalShortcuts` (org.freedesktop.portal.GlobalShortcuts): the portal pins app identity PER D-BUS CONNECTION at its first portal call, and on GNOME Qt's portal platform theme touches the Settings portal during QGuiApplication construction - the shared bus is already pinned to app id "" for terminal/AppImage launches, and gnome-control-center's shortcuts provider silently DISCARDS BindShortcuts from an empty app id (code 2 → hotkey UI collapses to the compositor-binds card). So ALL GlobalShortcuts traffic runs on a private bus connection whose first call is `Registry.Register` (re-issued after a portal restart - the association is in-memory portal-side). GNOME also enforces the spec's one-BindShortcuts-per-session; re-binds ride the fresh-session retry. `UNISIC_HOTKEY_BACKEND=portal` forces this path on a KDE box for testing.
Deliberate choices: keep working via portals on non-KDE; clipboard mirrored through `wl-copy` when present (Wayland reliability); recording region = full-monitor stream cropped in ffmpeg (portals can't select regions). **Multi-monitor recording target**: the SYSTEM share dialog is the screen selector - do not add an app-side picker in front of it (tried in dev, rejected: it duplicates the portal's own monitor choice). The dual-monitor bug was the restore token suppressing that dialog while silently replaying an old share - including an "entire workspace" one, which recorded BOTH screens with no dialog to say otherwise. Fix in `GifRecorder::openPortalSession`: full-screen/replay recordings (`Screen` source) on a multi-monitor setup never SEND the stored token, so the portal dialog always appears and the user's pick there is authoritative; with one monitor the token keeps its silent-start convenience. Region recordings keep per-monitor tokens (`record/portalRestoreTokenMonitor@<name>`) and `onStreamReady` verifies the delivered stream with `StreamGeometry::streamMatchesScreen` (header-only, unit-tested in `tests/StreamGeometryTest.cpp`): position must match the target screen's top-left AND the size must not be a workspace stream (whose position equals a primary-monitor target, so size has to be checked too); the one legitimate mismatch - GNOME fractional scaling streaming the logical size - is recognized as a UNIFORM rescale that isn't the workspace union. On mismatch the token is wiped and the portal reopened once (picker shows), then it fails with an actionable message.
Clipboard history (KDE Plasma): `AppContext::copyImageToClipboard` - on Plasma/KWin (`org.kde.KWin` on the bus) images are re-asserted through **`KSystemClipboard`** (KF6::GuiAddons, `HAVE_KGUIADDONS`, a hard build requirement - there is no build in which this branch is absent) with an empty **`x-kde-force-image-copy`** marker MIME attached (`makeForceImageMime`). Without that hint Klipper leaves the capture pasteable-now but never copies it into clipboard **history**, so the shot vanishes as soon as anything else is copied (issue #51). `QClipboard::setImage`/`wl-copy` advertise only `image/png` and cannot attach an empty marker; `KSystemClipboard` sets the whole `QMimeData` over the wlr data-control protocol, which also lands **without a focused window** - so the KDE branch skips the `wl-copy` mirror entirely (it bumps `m_clipboardSeq` so a stale deferred mirror can't clobber it). Spectacle/Flameshot do exactly this. Verified empirically: with the hint the image persists in the selection after the setter process exits (Klipper now owns/serves it, adding its own `application/x-kde-onlyReplaceEmpty`); without it, the selection reverts to the previous entry. The plain `QClipboard::setImage` still runs first so synchronous local reads (X11, the smoke test) keep working. Fix guarded by `clipboardHistoryHintCheck()` in the F8 smoke test + a **Klipper clipboard history** Developer button.
After-capture pipeline: every enabled action (copy/save/upload/editor) fires independently and immediately in `AppContext::finishCapture` - the editor never blocks the others. A user-chosen program can run alongside them (`AppContext::runExternalAction` → `ExternalActionRunner`, Settings › Capture › External action). Two bounds are load-bearing and neither may be removed: `kMaxConcurrent = 4` is the backpressure at the only boundary that can pile up (holding the shutter queues one child process per capture), and a per-child `QTimer` ceiling stops a program that never exits - without it the capture's scratch PNG stays on disk and the callback never fires for the rest of the session. The ceiling is `Settings::externalActionTimeoutSec` (`actions/timeoutSec`, default `kDefaultTimeoutMs / 1000` = 120), because a number compiled in is a guess about somebody else's program and can only be corrected by a release. `runExternalAction` **clamps** it to `[kMinTimeoutSec, kMaxTimeoutSec]` = 10 s … 1 h; the clamp is at the call site, NOT in `ExternalActionRunner::run`, because the dev button and the F8 step deliberately arm a 1 s ceiling and a clamp inside `run` would turn that check into a five-second wait that always passes. The UI reads the same two constants through the CONSTANT properties `externalActionTimeoutMin/MaxSec`, so the field cannot offer a value the capture path would silently correct, and the F8 line prints the ceiling actually in force (with `clamped from N` when a hand-edited config asked for something out of range). `exportSettings` skips non-writable properties: importing one writes nothing, so exporting it only adds a key that cannot come back. Two extra post-capture affordances live here too: (a) **copy last capture** - a regular always-registered hotkey (`copy-last`, default Meta+Shift+C, `hotkeys/copyLast`): `finishCapture` retains the newest screenshot PNG-encoded off-thread (`m_lastCaptureData`, megabytes not a pinned QImage) and `copyLastCapture()` decodes + copies on demand. This REPLACED the 2s global Ctrl+C grab (it stole ordinary copies right after a capture); startup still releases AND unregisters the legacy `quick-copy` action so upgraded installs can't keep a stale Ctrl+C grab or a phantom KCM row. Spectacle-parity in-window Ctrl+C: the region overlay (`OverlayController::confirmAndCopy` + `takeCopyRequested`, screenshot flow only) confirms the selection and forces a clipboard copy even with auto-copy off, and the editor's Ctrl+C copies the composited image. (b) **floating preview** - clicking a capture-notification thumbnail calls `CaptureNotification::preview()` → `AppContext::openPreview` which dumps the full image to a temp PNG and opens `PreviewWindow.qml` with a `PreviewController`. With layer-shell the surface is FULLSCREEN with the wl input region masked to the visible card (`setInputRect`, same pattern as the capture popup) so the card drags as a plain QML item - the only smooth option, layer surfaces can't be system-moved and per-event margin repositioning diverges; pin toggles overlay/top layer. Fallback: normal frameless window + `startSystemMove` + stays-on-top hint. Opacity slider fades the card item (NOT `Window.opacity` - qtwayland silently ignores it). Bringing a file the OTHER way (in, not out) runs through one router: `AppContext::openPath()` (image → editor, recording → trim window, anything else → a toast) is what the Edit page's file dialog, the main window's `DropArea` (`openDroppedUrls`/`openImageData`) and Ctrl+V (`pasteFromClipboard` → `pasteMimeData`) all end in, so there is exactly one routing rule and no payload can land silently. What the file IS decides, never what the drag source or dialog filter claimed. A dropped/opened FILE keeps its path as the editor's `overwritePath` (Ctrl+S writes the original), pasted PIXELS deliberately do not (no file of their own → Ctrl+S saves a new capture). Remote urls are refused, never downloaded: a browser drag that only offers an http url gets a message; one that offers real `image/*` bytes goes through `openImageData`. The drop target lives at the WINDOW level (a page-level one would die with its `Loader`) and is a `DropArea`, which takes drag events only, so nothing below it stops being clickable. `pasteMimeData(const QMimeData *)` is split out of `pasteFromClipboard()` precisely so the dev check can exercise the routing without writing to the system clipboard: a check that clobbers what the user had copied is a bug, and a snapshot/restore of `QClipboard::mimeData()` cannot be faithful (delayed-rendering formats, plus a re-assert would duplicate the entry in Klipper's history). Filenames come from `AppContext::makeFileName()` (template tokens `%date% %time% %datetime% %unix% %rand%`, format/quality from settings). Settings export/import (`AppContext::exportSettings/importSettings`) serializes all `Settings` Q_PROPERTYs via the metaobject (not raw QSettings keys - those omit defaults) plus destinations. Settings keys: NEVER put a key in a QSettings group named "general"/"General" - that name collides with INI's magic General section (serializes `[%General]`, parses back as `"General/..."`, case-sensitive reads miss → resets to defaults every launch). General-tab settings are top-level bare keys (plain `[General]` section) for exactly this reason. CLI: `unisic --fullscreen|--region|--window|--measure|--monitor|--recapture|--gif|--export-settings <f>|--import-settings <f>`. `--monitor` = screen under the cursor (`CaptureManager::captureActiveScreen`: KWin `CaptureActiveScreen` resolves the pointer's screen compositor-side; elsewhere the `QCursor::pos()` hint + portal workspace crop). `--recapture` = repeat the last region shot: the overlay stores each confirmed selection as `capture/lastRegion` (`"<screen>|<x>,<y>,<w>,<h>"` in LOGICAL px of the named screen - survives the KWin-native vs portal-scaled freeze difference), `recaptureLastRegion()` re-captures that screen and crops after rescaling to the current image size.
Developer mode: a `UNISIC_DEV_BUILD` CMake flag (auto ON for local builds - i.e. `UNISIC_BUILD == "dev"` - OFF for CI releases) exposes a **Developer tab** in Settings (`App.devBuild`). A dev build is also a **fully separate app** from installed stable: app name `unisic-dev` (which moves all QStandardPaths: cache, history, U-2-Net model), desktop id `app.unisic.UnisicDev`, own single-instance socket, own config dir `~/.config/unisic-dev` (seeded from stable on first run with all hotkeys UNBOUND - the stable KGlobalAccel component still owns its keys) and own hotkey component `unisic-dev`; the tray icon gets an amber corner dot. `ensureDesktopFile()` writes the dev entry and removes the legacy dev-written shadow of `app.unisic.Unisic.desktop` in `~/.local/share/applications` (which used to hijack the stable menu entry). Both apps can run and be CLI-targeted side by side. It shows detected compositor capabilities (`App.capNativeNotification/capCustomNotification/capRecordBorder`), a full smoke test bound to **F8** (`AppContext::runSmokeTest`), and a **per-action button** for each path. **REQUIREMENT for every new user-facing feature/path: wire it into BOTH** (a) the sequential smoke test in `AppContext::runSmokeTest` (as a pass/fail/skip step) **and** (b) a dedicated per-action button in the SettingsPage Developer pane (reuse the public `Q_INVOKABLE`, or add a small `devTest*()` for non-capture paths). This keeps the dev harness an exhaustive, hand-checkable inventory of what the app can do. In a release build, capability-gated options are shown greyed-out with an explanation rather than hidden.
