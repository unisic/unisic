# QML design system, kit singletons, accessibility

Read before adding or restyling any control, page, or window.

- **Action controls never depend on hover.** The History tile's selection, star and action strip, plus the image-first notification's action layer, stay allocated and visible for pointer, touch and assistive technology. Hover changes colour only. A `UMenuButton` popup still counts as card hover (`cardHover.hovered || moreMenu.menuOpen`) so the card's colour does not flicker when the pointer crosses onto `Overlay.overlay`, but no control lifetime depends on that state. Cursor feedback such as the capture crosshair is the deliberate exception: it follows only the canvas under the pointer and never changes layout or exposes an action.
- **Use semantic `Theme` tokens, never component colour literals.** `mediaBase`/`mediaText` are contrast ink over arbitrary screenshots and video, `modalScrim` is the common modal backdrop, `release{New,Fixed,Improved,Changed,Removed}` colour changelog categories, `recordFrameContrast` outlines a recording region, and `mode{Shot,Measure,Ocr,Gif,Video}` (read through `Theme.modeColor(purpose)`, keyed by `OverlayController::purposeName()`) identify the capture mode on the overlay - fixed hues rather than palette-derived, because like the recording tokens they sit over a frozen screenshot, and `modeShot` defaults to the accent so an ordinary screenshot looks exactly as it always has. They are optional custom-theme JSON keys with fallbacks in `Theme.qml::_expand()`: adding one must extend `ThemeJson::optionalColorKeys()`, never `requiredColorKeys()`, so old community themes remain valid.

- **A setting that can only be seen mid-capture gets a preview in the page.** The capture overlay holds an exclusive keyboard grab over a frozen screen, so its options could not be checked without taking a real capture and coming back - the toolbar-position drop-down and the mode badge were missed entirely (user-reported). `UOverlayPreview` draws a mock screen at the top of the "Capture overlay" card instead (Appearance tab, not Capture: the card is what the overlay LOOKS like, and the Capture tab was already the crowded one the options got lost in): badge or centred mode glyph, mode frame, selection with handles, guides, loupe and the toolbar placed by a scaled copy of `OverlayWindow`'s own rules, live off `App.settings`, with a mode picker that drives ONLY the picture and writes no setting. Same shape as `UNotifPreview` and the watermark preview, and pure QML - it approximates the overlay rather than instantiating it, because the real one needs a portal freeze and an `AnnotationCanvas` per monitor. What it must never do is drift: `AppContext::overlayPreviewCheck()` builds the real component and asserts one entry per `OverlayController::purposeName()` plus a toolbar that stays on screen in all ten positions and one indicator per `overlayModeStyle` (dev button + smoke step), because a preview that teaches the wrong thing is worse than none. The `icon` style is the one that needs the assert: `UModeGlyph` cuts the selection OUT of the glyph (four clipped copies around the hole - one item cannot have a hole, and a mask effect needs a GPU path the software renderer has not got), so the mock selection must both reach the glyph and leave part of it standing, or the style demonstrates either an uncut mark or an empty screen. The overlay and the mock instantiate the SAME component, which is the only reason the mock cannot get this one wrong.
- `qml/` - fully custom SwiftUI-like design system (**no Kirigami/Breeze**; QQuickStyle forced to "Basic"): `Theme.qml` singleton (9 palettes computed from tokens; keep property names stable - 19 files depend on them) + `ToolCatalog.qml` singleton (single source of annotation tools **and their letter shortcuts**; both toolbars build from `visibleFor(ctx, hiddenTools)`, both keyboard hosts resolve through `toolForShortcut()`) + `components/` (UButton, USwitch, UIcon, UComboBox, …). **Four kit singletons own the cross-cutting rules, and each is the ONLY copy of its rule** - extend them, never write a rival: `UKeys` (keyboard activation: a dedicated `Keys.on<Key>Pressed` runs BEFORE `Keys.onPressed`, ignores modifiers and arrives pre-accepted, so an unguarded handler swallows the window's own chords - `UKeys.activate/claim/unmodified` hand a chord back to the bubbling path, KeypadModifier masked so numpad Enter still acts), `UFlyout` (containment: every dropdown/menu/picker is parented to its ANCHOR, not `Overlay.overlay` - Qt's positioner then tracks the anchor, the window and every ancestor, `margins` clamps, and the kit adds only what Qt does not do, namely flip-above and shrink-to-fit-with-internal-scroll; a flyout never covers its own field), `UNameBridge` (a row caption becomes the control's accessible NAME when it is alone in the row and its DESCRIPTION when several share it - one caption is one identity), `UFocusRing` (the ring, plus THE INSET RULE). `FocusScroll` is the fourth member of the `MiddleScroll`/`WheelBoost` family: a plain Flickable is not a ScrollView, so Tab could land on a control far below the fold with `contentY` untouched; it reveals only items COMPLETELY off screen, because a click is a focus change too and scrolling a partly visible control into view would move the page under the pointer that clicked it. Icons are `iconName` (freedesktop names) via `UIcon`, not emoji. **Every resizable frameless window carries `UWindowResizer` as its LAST content child**: a window that draws its own title bar gets no compositor resize border, so without it the edges are dead - no resize cursor, no drag (user-reported on main/editor/trim). Eight edge/corner MouseAreas in the outer 7 px set the resize cursors and hand the drag to `startSystemResize` (native on Wayland and X11); zones go quiet when maximized/fullscreen, `active` is bound to `!useSystemDecoration`, and the top band deliberately outranks the title bar's move area - resize beats move at the border, like a decorated window. A new frameless-but-fixed-size surface (popup, overlay, border frame) does NOT get one. Windows are created from C++ via QQmlComponent with per-window QQmlContext (`editorSession`, `overlayController` context properties). Layout rules that are load-bearing, not taste: nothing may move or appear under the pointer (colour feedback only), a control never toggles `visible` in a row (it stays and disables, or the row reflows), every option is a `USettingRow` bordered card on ONE full-width grid, and the main pages must still fit above the fold at 1060×700, which is why the Capture tiles are 140 px tall and its option grid is exactly 8 cells (delay / repeat last region / upload server + the five after-capture toggles); a ninth strands itself on a fifth row AND overflows the fold.
- **Template-variable chips float, never join the layout.** `UVarBar` is ONE bar per form, parented to the card or pane ABOVE the fields (last child, `z: 2`) and pointed at whichever field has focus. Parented into the field's own row instead, the row appearing on focus pushes everything below it down at the moment the field is clicked - the form rearranges under the pointer using it, which is the one thing layout here may never do. It positions itself with `mapFromItem` (a function, so the bindings read `viewport.contentY`/`contentX` for their dependency) and clamps to the viewport, so a field at the fold still gets its chips on screen. It takes the FIELD's `x` and `width`, not the viewport's: sized to the viewport it overhung the field on both sides and read as a panel of its own instead of that field's variables (user-reported). `vars` always comes from the C++ that performs the substitution (`UploadManager::templateHelp`, `FilenameTemplate::help`) - a chip for a token the sender ignores looks like it worked. The chips are never Tab stops (the bar comes and goes with focus), so every field offering them also names its variables in a visible caption or hint. `UTextField.tokenPattern` paints the same tokens as pills behind the text, `text` staying exactly the string that gets saved. Those pills sit in a `pillBox` sibling declared BEFORE the `TextInput`, not inside it: `clip: true` clips a child whatever its `z`, so a pill drawn wider than its glyphs lost exactly its padding and read as running past the field's edge (user-reported). `pillBox` is the input's rect grown by that padding and clips there instead, so a token scrolled out of view still loses its half. A pill takes at most HALF the blank beside it (`input.tokenGap`), because tokens are routinely written back to back (`$text$$text$`) and two pills each grown by the full padding crossed each other's rounded borders. `insertToken` remembers where it parked the caret (`parkedCaret`/`parkedEnd`, cleared by any typing): a chip clicked while the caret is still exactly there steps past that token first, or two clicks nest one variable inside another (`$json:$regex:$$`, which resolves to nothing) and every further click adds an orphaned `$`.
- **Accessibility contract** (kit components + app QML): Tab walks the interface, the focused control draws a `UFocusRing` in the accent colour, Space/Enter activates, and every control carries `Accessible.role/name` plus its state. Composite items name themselves ONCE: the container gets the assembled name and each label inside sets `Accessible.ignored: true` (ignoring the Column instead only promotes its children). Two places are deliberately OUT of the tab chain and must stay out: **history tiles** (the `GridView` owns keyboard navigation through `currentIndex` + its own `Keys` handler; a per-tile tab stop would make Tab walk a hundred captures and move a different cursor than the ring shows; AT-SPI still enumerates and Presses them), and the **capture overlay's** toolbar (`focusable: false` / `activeFocusOnTab: false` on every chip and button): there Space/Enter mean "confirm the capture" and the overlay holds an exclusive keyboard grab, so a focused chip would swallow the gesture that finishes the shot. The overlay keeps its own vocabulary instead: the tool letters from `ToolCatalog`, Space/Enter to confirm, Escape to cancel. Key handlers on focusable items are `Keys.onSpacePressed`/`onReturnPressed`/`onEnterPressed`, never a blanket `Keys.onPressed`, or a focused tile eats the window's `Ctrl+1`…`Ctrl+6`/`Ctrl+V`.
