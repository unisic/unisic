# QML design system, kit singletons, accessibility

Read before adding or restyling any control, page, or window.

- **Action controls never depend on hover.** The History tile's selection, star and action strip, plus the image-first notification's action layer, stay allocated and visible for pointer, touch and assistive technology. Hover changes colour only. A `UMenuButton` popup still counts as card hover (`cardHover.hovered || moreMenu.menuOpen`) so the card's colour does not flicker when the pointer crosses onto `Overlay.overlay`, but no control lifetime depends on that state. Cursor feedback such as the capture crosshair is the deliberate exception: it follows only the canvas under the pointer and never changes layout or exposes an action.
- **Use semantic `Theme` tokens, never component colour literals.** `mediaBase`/`mediaText` are contrast ink over arbitrary screenshots and video, `modalScrim` is the common modal backdrop, `release{New,Fixed,Improved,Changed,Removed}` colour changelog categories, `recordFrameContrast` outlines a recording region, and `mode{Shot,Measure,Ocr,Gif,Video}` (read through `Theme.modeColor(purpose)`, keyed by `OverlayController::purposeName()`) identify the capture mode on the overlay - fixed hues rather than palette-derived, because like the recording tokens they sit over a frozen screenshot, and `modeShot` defaults to the accent so an ordinary screenshot looks exactly as it always has. They are optional custom-theme JSON keys with fallbacks in `Theme.qml::_expand()`: adding one must extend `ThemeJson::optionalColorKeys()`, never `requiredColorKeys()`, so old community themes remain valid.

- **One wheel speed everywhere.** Every wheelable Flickable, ListView and GridView carries `WheelBoost { flickable: <id> }` and nothing else: it is Chromium's Linux wheel (120 px per notch, no fast-spin multiplier, an ease-in-out glide of 200 ms for one notch that a new notch retargets, touchpad pixels 1:1), and it has no step property on purpose, because per-page steps are what made Settings race while History crawled. It reparents itself into the view's `contentItem`: a ListView or GridView keeps declared children as direct children of the view, where the view's own wheel physics (72 px per notch) won and the component was never called. Only the annotation canvas (wheel = zoom/pan) stays out.
- **A setting that can only be seen mid-capture gets a preview in the page.** The capture overlay holds an exclusive keyboard grab over a frozen screen, so its options could not be checked without taking a real capture and coming back - the toolbar-position drop-down and the mode badge were missed entirely (user-reported). `UOverlayPreview` draws a mock screen at the top of the "Capture overlay" card instead (Appearance tab, not Capture: the card is what the overlay LOOKS like, and the Capture tab was already the crowded one the options got lost in): badge or centred mode glyph, mode frame, selection with handles, guides, loupe and the toolbar placed by a scaled copy of `OverlayWindow`'s own rules, live off `App.settings`, with a mode picker that drives ONLY the picture and writes no setting. Same shape as `UNotifPreview` and the watermark preview, and pure QML - it approximates the overlay rather than instantiating it, because the real one needs a portal freeze and an `AnnotationCanvas` per monitor. What it must never do is drift: `AppContext::overlayPreviewCheck()` builds the real component and asserts one entry per `OverlayController::purposeName()` plus a toolbar that stays on screen in all ten positions and one indicator per `overlayModeStyle` (dev button + smoke step), because a preview that teaches the wrong thing is worse than none. The `icon` style is the one that needs the assert: `UModeGlyph` cuts the selection OUT of the glyph (four clipped copies around the hole - one item cannot have a hole, and a mask effect needs a GPU path the software renderer has not got), so the mock selection must both reach the glyph and leave part of it standing, or the style demonstrates either an uncut mark or an empty screen. The overlay and the mock instantiate the SAME component, which is the only reason the mock cannot get this one wrong.
- `qml/` - fully custom SwiftUI-like design system (**no Kirigami/Breeze**; QQuickStyle forced to "Basic"): `Theme.qml` singleton (9 palettes computed from tokens; keep property names stable - 19 files depend on them) + `ToolCatalog.qml` singleton (single source of annotation tools **and their letter shortcuts**; both toolbars build from `visibleFor(ctx, hiddenTools)`, both keyboard hosts resolve through `toolForShortcut()`) + `components/` (UButton, USwitch, UIcon, UComboBox, …). **Four kit singletons own the cross-cutting rules, and each is the ONLY copy of its rule** - extend them, never write a rival: `UKeys` (keyboard activation: a dedicated `Keys.on<Key>Pressed` runs BEFORE `Keys.onPressed`, ignores modifiers and arrives pre-accepted, so an unguarded handler swallows the window's own chords - `UKeys.activate/claim/unmodified` hand a chord back to the bubbling path, KeypadModifier masked so numpad Enter still acts), `UFlyout` (containment: every dropdown/menu/picker is parented to its ANCHOR, not `Overlay.overlay` - Qt's positioner then tracks the anchor, the window and every ancestor, `margins` clamps, and the kit adds only what Qt does not do, namely flip-above and shrink-to-fit-with-internal-scroll; a flyout never covers its own field), `UNameBridge` (a row caption becomes the control's accessible NAME when it is alone in the row and its DESCRIPTION when several share it - one caption is one identity), `UFocusRing` (the ring, plus THE INSET RULE). `FocusScroll` is the fourth member of the `MiddleScroll`/`WheelBoost` family: a plain Flickable is not a ScrollView, so Tab could land on a control far below the fold with `contentY` untouched; it reveals only items COMPLETELY off screen, because a click is a focus change too and scrolling a partly visible control into view would move the page under the pointer that clicked it. Icons are `iconName` (freedesktop names) via `UIcon`, not emoji. **Every resizable frameless window carries `UWindowResizer` as its LAST content child**: a window that draws its own title bar gets no compositor resize border, so without it the edges are dead - no resize cursor, no drag (user-reported on main/editor/trim). Eight edge/corner MouseAreas in the outer 7 px set the resize cursors and hand the drag to `startSystemResize` (native on Wayland and X11); zones go quiet when maximized/fullscreen, `active` is bound to `!useSystemDecoration`, and the top band deliberately outranks the title bar's move area - resize beats move at the border, like a decorated window. A new frameless-but-fixed-size surface (popup, overlay, border frame) does NOT get one. Windows are created from C++ via QQmlComponent with per-window QQmlContext (`editorSession`, `overlayController` context properties). Layout rules that are load-bearing, not taste: nothing may move or appear under the pointer (colour feedback only), a control never toggles `visible` in a row (it stays and disables, or the row reflows), every option is a `USettingRow` bordered card on ONE full-width grid, and the main pages must still fit above the fold at 1060×700. The Capture page follows the redesign mock's sizes 1:1 at the mock's 1440x900 and goes `compact` below it (see the main window note below); its after-capture options live in the right-hand column, not in a grid.
- **A collapsed group must stay searchable.** `SettingsPage.qml`'s `DisclosureRow` (local, not a kit component - one pane wanting a disclosure is not a design-system control) hides the rows placed under it behind one clickable title + summary + chevron; the Hotkeys pane uses it so the five captures everyone presses are not buried under the ones that need a build option or a habit. The rows it hides stay ordinary `SettingRow`s and are `visible: <disc>.expanded || page.searchActive`, because `collectRows()` SKIPS invisible subtrees - a collapsed row would silently vanish from settings search. `searchActive` alone is not enough either: `jumpTo()` clears the query, so the row it just highlighted would collapse back out of sight. Hence `SettingRow.discloser` - the row names the disclosure it lives in and `jumpTo()` opens it on the way. Set `visible` (not `available`) only when the option cannot exist on this system at all: greying out says "install something", hiding says "not here".
- **The editor has two layouts and one set of controls.** `EditorWindow.qml` reads `Settings::editorLayout` (`ui/editorLayout`, `"panels"` default or `"floating"`, Settings > Editor > Layout) into `floatingLayout`. Panels: tool rail on the left, the active tool's options in a 320 px inspector column (`inspectorWidth`, `Theme.spacingL` padding on every side) on the right, zoom in a status line. Floating: the image gets the whole window and the same items sit in pills over its edges. Every control is the SAME item in both, only re-anchored, so shortcuts, Tab order and the smoke test's `objectName`s (`editorToolRail`, `editorToolOptions`, `editorActions`, `editorInspector`, `editorStatusBar`, `editorCanvas`) hold in both; never fork a control per layout. `layoutOverride` lets the smoke test (`editorLayoutCheck` in `SmokeTests.cpp`, F8 step 3 and Developer > Editor layouts) lay one editor out both ways without touching the saved setting: no bar may leave the window or cover the fitted image, and the Text tool's options (the widest set) must not spill out of the inspector or, floating, out of the window or over the status line. The window's minimum width grows with the inspector, so read the window size after a flip, not before. `editorChromeCheck` (F8 step 3, Developer > Editor chrome) covers the redesign's own pieces: the inspector's shape list has one row per shape (`editorShapeList`) and a row click selects that shape, Fit and 1:1 set the zoom they name, the back button shows, and floating folds the tools into the three group chips with the whole-image pill (`editorWholeImage`) inside the window. An elided `Text`'s `implicitWidth` inside its own width binding is a binding loop: measure with `TextMetrics` (the title pill does). The shape actions (Duplicate, Arrange, Delete) sit in `shapesRow` beside the shape chips; Arrange is a `UMenuButton { flat: true }`, the kit's chip-look trigger, because a tonal pill in a row of chips reads as the active tool. Size anything inside these Flows with `implicitWidth`/`implicitHeight`, not `width`: `flowWrap()` measures the implicit size, and a 2 px short sum dropped the separator onto a line of its own. A `ToolPropsBar` `Cell` cannot wrap inside itself, so a `DotGroup` longer than `maxWidth` (the swatches plus recent colours in the inspector, the stickers) wraps its OWN dots: `reserve` is what else its Cell puts on that line, `balanced: true` evens the lines (stickers 5/5/3, not 6/6/1) and stays off where a shorter line would pull the next Divider onto a line start. A group wraps to `groupLimit` (the host's raw bound, defaults to `maxWidth`), never to a `maxWidth` the host derived from the cells: the editor's floating pill passes `flowBalanced(propsBar, ...)`, which reads the cells' widths, so a group wrapping to it changed the cells it was measured from and the Cell's `Row` re-polished itself in a loop (`possible QQuickItem::polish() loop`, a 1.3 s stall on picking the Sticker tool). Its unwrapped width is summed from the dots' `width`, because `ColorDot` sets no `implicitWidth`, and a wrapped group's Cell reports one line (`lineHeight`) so it alone grows taller. No vertical anchors on anything inside a Flow. The right-click shape menu is a hidden `UMenuButton` with `anchorItem` on a 1 px item under the pointer and `preferAbove: false`; the hidden trigger cannot take focus back, so `onMenuOpenChanged` returns it to `shortcutScope`.
- **The main window is a rail and a header, and the Capture, Record, Clips and Edit pages have the side columns.** Both follow the redesign mock (`Main.dc.html`) 1:1; change them against it, not by eye. `Main.qml`: a 76 px navigation rail of `RailItem` (a `SidebarItem { stacked: true }`, 60 px wide; kit: icon over an 11 px label that shrinks to 9 px before eliding, for German and Italian) and a 44 px header (`chromeTop`) that stays under system decorations because it carries the version chip and the recording pill. The page area is `Theme.primary`, or `Theme.background` where a palette makes primary and surface the same colour, so the cards still stand off it. The rail and the Capture page draw the mock's own line icons, `line-*.svg` in the kit's `resources/icons/sym/` (24 px box, 1.75 stroke); the names are unique, so the system icon theme never replaces them. `HeaderSearch.qml` sits centred between the header's left and right groups (160 to 440 px) and `Ctrl+K` focuses it: up to six capture actions and pages, every matching Settings category, then one row that hands the words to the Settings search (`Main.openSettingsAt(tab, query)`), then up to four captures from a `HistoryFilterModel` that filters only while the list is open. Its `settingsTabs` must stay in `SettingsPage.tabNames` order, since the index is the tab; `headerSearchCheck()` (F8, Developer > Header search) asserts that through `openSettingsAt`. `CapturePage.qml`, `RecordPage.qml`, `ClipsPage.qml` and `EditPage.qml` are the four sanctioned exceptions to "one full-width grid per page" (`AGENTS.md` §8): tiles and Recent on the left, a 300 px settings column (`Inspector.qml`) on the right. All four build from the same pieces in `qml/components/` (`PageTitle`, `SectionLabel`, `Link`, `MiniSwitch`, `SegmentedControl`, `SourceTile`, `ActionTile`, `TileArt`, `RecentStrip`, `Inspector`, `InspectorRow`, `Hotkeys.js`); strings that moved there out of CapturePage keep `qsTranslate("CapturePage", ...)` so their translations carried over. The tile art is drawn at 220x132 from plain Rectangles (no QtQuick.Shapes, which Debian packages separately) and scales down in a narrower tile. **`compact`** (a page under 760 px tall, or too narrow for four 200 px tiles beside the column, which covers the default 1060x700 window) is what keeps the page above the fold there: tighter gaps and paddings, the four tiles and the four More tiles each in one row (130 px minimum), the art scaled to the tile, two-line subtitles. The mock's sizes return as soon as the window has the room. Recent always shows at least one whole row: when a 150 px tile would be cut by the bottom, `perRow` grows (up to six) until the row fits. A bigger window goes to Recent in whole rows (as many as fit without scrolling, thumbnails up to square, corners rounded by one shared `MultiEffect` mask). Recent is a non-interactive GridView with no cache buffer that still builds part of the row after the last one, so a delegate hides itself by index (`shown`) and `capturePageCheck()` (F8, Developer > Capture page layout) counts distinct shown indexes, at the user's real window size, and also asserts the four delay presets, a non-empty status line and, from 1060x700 up, that neither the page nor the right column (`captureAside`) scrolls. The right column lists the after-capture steps in `AppContext::finishCapture` order (save, copy, upload, editor; the numbers and the subtitle say so), then the delay, cursor and Repeat last region, the upload server, and a status line pinned to the bottom when there is room: the session, `App.screenshotBackend()` and the recording path. Hotkeys render through `Kbd.qml`, one keycap per key; a More tile drops its key before its title would elide. **Record page**: the same `compact` rule for three tiles; Video/GIF is a `SegmentedControl` beside the title (still `Settings::recordPageMode`), the Screen/Region/Window `SourceTile`s draw `TileArt` with `rec: true` (the REC badge over the recorded area, never animated), Pause/Stop/replay are `ActionTile`s that only enable/disable, and Recent is a `RecentStrip` over a `HistoryFilterModel` filtered to `video` or `gif` (one category, so instant-replay clips stay in History). Its right column (`recordAside`) swaps whole section bodies with the mode, never single rows; Format sits inline beside its label so the Video column still fits at 1060x700, and in `compact` an `InspectorRow` cuts its `sub` to two lines (as the compact Capture tiles do), the full text on hover through `UHoverTip` and in the control's accessible description. Measured at 1060x700 with that cut: 71 px to spare in English, Polish, German and French, 54 px in Russian; without it Polish ran 12 px over and the column scrolled. GIF quality is a list, not segments: three segments cut its labels short in every other language. **Edit page**: the same `compact` rule for two tiles; a `HeaderButton` Paste (with `kbd`) beside the title, Edit an image / Trim a video as `SourceTile`s drawing `TileArt.EditImageArt` / `TrimVideoArt` with `subLines: 1` (a held second line pushed Recent below the fold at 1060x700) and their `edit-image` / `trim-video` keys, whose "set one" link opens the Settings search on the row's caption (`openSettings(-1, query)`), as the Record page's Screen and Window tiles do, the three Share actions as `ActionTile`s, and a `RecentStrip` over all of `App.history` with `openToEdit: true`, so a tile goes through `AppContext::openPath` (an image to the editor, a recording to the trim window) instead of Capture's preview. The Edit page has no mock of its own; it follows Capture's. Its right column (`editAside`) is a subset of Settings > Editor (layout, stroke colour, stroke width, text size, the two reset switches; `Manage` opens that tab) in `qsTranslate("SettingsPage", ...)` so the strings keep one translation, then the page's "Good to know" notes.
- **History page** is in the same language with ONE column (it is content; no settings column): `PageTitle` with the count as its subtitle, search and Clear all (`HeaderButton.qml`, the Capture header button's look) on the right, then the kind filter as a `SegmentedControl` (segments share the widest label's width) beside Starred/Uploaded as `FilterToggle.qml` pills (independent toggles, so not segments; their label weight never changes, or the pill would widen under the pointer). The selection bar takes that row's place. The day group is a `SectionLabel` over the grid that follows the topmost row (GridView has no sections; regrouping the model would rebuild every tile on a star toggle). Tiles are Recent's (16:10 thumbnail, one shared `MultiEffect` corner mask, layer only once the image is loaded, one badge, monospace name over the meta line) plus the History controls; the grid sits `tileInset` wider than the column so the thumbnails, not their cells, line up with the header. The selection ring is drawn over the picture: thickening the thumbnail's own border would shrink and reload the image on every toggle.
- **Settings page** takes the same language through its local components, not row by row: History's header (`PageTitle`, a line under it, then the settings search, Import and Export as `HeaderButton`s on the right; the search field is the one elastic control, 150 to 240 px, and comes first so Tab still reaches it before the commands), Capture's 40 px margins and `compact` top gap, `SectionTitle` as a `SectionLabel`, `SettingRow`/`DisclosureRow`/search results on the tiles' hairline (`page.cardBorder`, warming to `cardBorderHover` only on the clickable cards) with the `InspectorRow` type sizes, and `NavItem` with the main rail's selected fill (`Theme.secondary`) and the raised surface on hover. Rows, panes, search, the Developer pane and every `objectName` are unchanged; a `SettingRow`'s `problem` frame (a hotkey conflict) still outranks the hairline.
- **Servers page** (`DestinationsPage.qml`) is in the same language with ONE column, like History: `PageTitle` and its subtitle, Add custom server and Import .sxcu as `HeaderButton`s, pinned, so only the list scrolls. The Failure Chain switch is a `MiniSwitch` on the list's own `SectionLabel` ("Upload order"), because the order is the chain, with its explanation under it (two lines in `compact`, the full text on hover and in the switch's accessible description). The rows take `ActionTile`'s look (56 px, radius 10, icon square, title over the request URL) but not its click or hover: the row is a list entry and the grip, Edit and Delete are its controls. The action box keeps room for both buttons and lays out from the right, so Edit stays in one column whether a row can be deleted or not. Header and list cap at 1120 px so a maximized window does not put Edit 1.6k px from its name. Measured at 1060x700: the seven shipped servers fit without scrolling in English and Polish. The edit sheet keeps its kit controls.
- **Template-variable chips float, never join the layout.** `UVarBar` is ONE bar per form, parented to the card or pane ABOVE the fields (last child, `z: 2`) and pointed at whichever field has focus. Parented into the field's own row instead, the row appearing on focus pushes everything below it down at the moment the field is clicked - the form rearranges under the pointer using it, which is the one thing layout here may never do. It positions itself with `mapFromItem` (a function, so the bindings read `viewport.contentY`/`contentX` for their dependency) and clamps to the viewport, so a field at the fold still gets its chips on screen. It takes the FIELD's `x` and `width`, not the viewport's: sized to the viewport it overhung the field on both sides and read as a panel of its own instead of that field's variables (user-reported). `vars` always comes from the C++ that performs the substitution (`UploadManager::templateHelp`, `FilenameTemplate::help`) - a chip for a token the sender ignores looks like it worked. The chips are never Tab stops (the bar comes and goes with focus), so every field offering them also names its variables in a visible caption or hint. `UTextField.tokenPattern` paints the same tokens as pills behind the text, `text` staying exactly the string that gets saved. Those pills sit in a `pillBox` sibling declared BEFORE the `TextInput`, not inside it: `clip: true` clips a child whatever its `z`, so a pill drawn wider than its glyphs lost exactly its padding and read as running past the field's edge (user-reported). `pillBox` is the input's rect grown by that padding and clips there instead, so a token scrolled out of view still loses its half. A pill takes at most HALF the blank beside it (`input.tokenGap`), because tokens are routinely written back to back (`$text$$text$`) and two pills each grown by the full padding crossed each other's rounded borders. `insertToken` remembers where it parked the caret (`parkedCaret`/`parkedEnd`, cleared by any typing): a chip clicked while the caret is still exactly there steps past that token first, or two clicks nest one variable inside another (`$json:$regex:$$`, which resolves to nothing) and every further click adds an orphaned `$`.
- **Accessibility contract** (kit components + app QML): Tab walks the interface, the focused control draws a `UFocusRing` in the accent colour, Space/Enter activates, and every control carries `Accessible.role/name` plus its state. Composite items name themselves ONCE: the container gets the assembled name and each label inside sets `Accessible.ignored: true` (ignoring the Column instead only promotes its children). Two places are deliberately OUT of the tab chain and must stay out: **history tiles** (the `GridView` owns keyboard navigation through `currentIndex` + its own `Keys` handler; a per-tile tab stop would make Tab walk a hundred captures and move a different cursor than the ring shows; AT-SPI still enumerates and Presses them), and the **capture overlay's** toolbar (`focusable: false` / `activeFocusOnTab: false` on every chip and button): there Space/Enter mean "confirm the capture" and the overlay holds an exclusive keyboard grab, so a focused chip would swallow the gesture that finishes the shot. The overlay keeps its own vocabulary instead: the tool letters from `ToolCatalog`, Space/Enter to confirm, Escape to cancel. Key handlers on focusable items are `Keys.onSpacePressed`/`onReturnPressed`/`onEnterPressed`, never a blanket `Keys.onPressed`, or a focused tile eats the window's `Ctrl+1`…`Ctrl+6`/`Ctrl+V`.
